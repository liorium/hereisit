기준일: 2026-10-06 한국 시간. 소스 기준: `2c1a696`.
이번 작업은 조사·읽기 전용 운영 조회·기존 단위 테스트와 함수 수준 재현이다.

사이트 전체나 Next.js/TypeScript를 교체할 근거는 없다. 서버 압축 허용과 외부 비용 집계의
결합을 고치고, 추가 이미지 도구의 누락된 제한·출력 검증을 먼저 보완한다.

새 엔진은 아래 운영 장애나 브라우저 도구 결함을 자동으로 해결하지 않는다.

## 현재 확인한 범위

  모두 제목·H1·description·canonical·CSP 헤더가 존재했다. 개인 도구/워크플로는 noindex다.
  이는 실제 조작, 접근성, 검색 색인, 렌더링 속도 또는 파일 처리 성공을 증명하지 않는다.

  새 익명 세션의 `/v1/policy`는 `SERVER_PROCESSING_DISABLED`를 반환했다.
  서버 압축을 사용할 수 없다는 사실은 현재 조회로 확인했다.
  현재 운영 DB 내부의 정확한 차단 사유와 활성 엔진 버전은 이번에 재조회하지 않았다.
- 최근 조회한 운영 점검 12회가 실패했다. 최신 기록에서도 페이지/health는 통과하지만

  [운영 점검 기록](https://github.com/liorium/hereisit/actions/runs/37275938867).
- 9월 22일 공개 허용 검사와 이미지 품질 검증의 성공 기록은 있다.
  과거 성공이 현재 사용 가능성을 보장하지 않는다.
  [공개 허용](https://github.com/liorium/hereisit/actions/runs/35721393892),
  [품질 검증](https://github.com/liorium/hereisit/actions/runs/35685662479).

## 1. 서버 압축 차단과 비용 집계 결합 — P1

**근거:** `apps/api-worker/src/hourly-cost-sealer.ts:275`는 미완료 데이터가 기한을 넘으면
`COST_ACCOUNTING_INCOMPLETE`로 전체 회로를 연다. `routes/policy.ts`와
`d1-job-repository.ts`는 회로가 열려 있으면 서버 작업을 거부한다.
`cost-accounting-runtime.ts`는 외부 조회뿐 아니라 내부 검증/DB 오류도 일부 포괄적으로
`incomplete`로 합친다. 따라서 단순히 모든 incomplete를 허용해서는 안 된다.

**수정:** 기존 [승인된 집계 분리 설계](../superpowers/specs/2026-10-05-processing-accounting-isolation-design.md)를
재사용한다. 검증된 외부 통계 장애는 별도 상태·알림으로 기록하고, 기존 처리량·속도·대기·
컨테이너·시간·메모리 제한 안에서 작업을 허용한다. DB 손상, 삭제 실패, 결과 검증 실패와
실제 비용 초과에 대한 차단은 유지한다. 과거 누락 비용은 0원으로 간주하지 않는다.

**완료 기준:** 통계 403/시간 초과 상황에서도 적격 작업이 예약·처리되고, 동시 발생한
삭제/검증 실패에는 차단이 유지된다. 현재 운영 상태를 재조회한 뒤 기존 절차로 배포하고
일반 공개 경로의 업로드·압축·다운로드·삭제까지 확인해야 복구로 판정한다.

## 2. 추가 이미지 도구의 용량·픽셀 제한 누락 — P1

**근거:** `apps/web/src/components/image-extra-workbench.tsx:596`의 `chooseFiles`는
형식과 파일 개수만 확인한다. 도구 설정에 있는 `maxFileBytes`, `maxTotalBytes`를 소비하지
않고, 디코딩 전 입력 픽셀 제한도 이 경로에는 없다. JPG 변환·편집·밈·확대·흐림·배경 제거
등이 같은 경로를 사용한다. 원본 미리보기도 파일 선택 즉시 object URL로 제공한다.

`fitDimensions`는 원본 크기로 제한 비율을 계산한 다음 확대 배율을 곱한다.
실제 소스 함수를 TypeScript로 변환해 이미지 할당 없이 실행한 결과:

| 입력 | 요청 | 계산된 출력 | 결과 |
| --- | --- | --- | --- |
| 4000×3000 | 4배 | 16000×12000, 192,000,000픽셀 | 선언된 25,000,000픽셀 초과 |

이 출력의 RGBA 버퍼 하나만 768,000,000바이트다. 실제 브라우저 최대 메모리를 측정한 값은
아니며 디코딩·출력 버퍼가 중첩되면 사용량은 더 늘 수 있다.

**수정:** 미리보기/디코딩 전에 파일당·일괄 크기를 검사하고 기존 이미지 검사 기능으로
지원되는 입력의 크기를 확인한다. 요청한 최종 출력 크기로 픽셀·변 길이를 검사한다.
정확한 2배/4배 결과가 한도를 넘으면 이유와 가능한 선택을 안내하고, 조용히 배율을 줄이지 않는다.
일반 편집 경로에도 입력/출력·보관 결과·ZIP 합계 제한을 적용한다.
기존 `packages/image-tool`과 `packages/browser-runtime/src/image-pipeline.ts`의 검증을
재사용하되 지원 형식 차이를 확인한다. 별도 범용 플랫폼을 만들 필요는 없다.

**완료 기준:** 초과 파일·일괄 입력은 미리보기 생성 전 거부되고, 4000×3000의 4배 요청은
대형 비트맵 생성 전에 거부된다. 경계값과 2배/4배 계산을 순수 단위 테스트로 검증한다.
CI 브라우저 검증으로 실제 결과 크기·오류 안내·연속 작업 자원 해제를 확인한다.

## 3. 확대 대체 경로가 원본 크기를 성공으로 반환 — P1

**근거:** 같은 파일의 `loadRenderSource`는 `createImageBitmap`이 없거나 실패하면
`loadImage`로 넘어간다. 이 분기는 요청 배율을 적용하지 않고 원본 크기를 반환한다.
`renderFile`도 그 크기로 canvas를 만들고 호출자는 완료로 표시한다.
실제 함수를 추출하고 이미지 로더만 100×100으로 대체한 재현에서 4배 요청이 100×100을 반환했다.
이는 함수 수준 재현이며 실제 특정 브라우저에서 실패 빈도를 측정한 결과는 아니다.

**수정:** 모든 디코더 경로가 동일한 최종 출력 계획을 사용하게 한다. 대체 경로에서도
canvas에 정확한 요청 크기로 그리거나, 지원 불가 오류로 종료한다. 완료 전에 실제 크기를 검증한다.

**완료 기준:** 디코더 부재와 디코더 실패를 각각 재현해 100×100의 4배 결과가
400×400 또는 명확한 실패가 되며 원본 크기의 성공은 발생하지 않는다.

## 4. 비용 상한·알림·안전 검사 연결 미완성 — P1

**근거:** `maximumLiveCostPer1000Microusd`, `maximumProjectedMonthlyCostMicrousd`는
`env.ts`에서 파싱/검증하지만 운영 코드에서 초과 판정으로 사용하는 경로가 검색되지 않았다.
처리 단위별 일일 제한은 존재하지만 통화 단위 청구 상한과 같지 않다.
`operational_alert_state` 테이블과 설정 생성기의 `ALERT_EMAIL` 바인딩은 있으나 실제
메일 발송 경로는 없다. CI 실패 알림과 별도 운영 알림의 발송 완료를 혼동하면 안 된다.

`sweeper.ts:89`는 비용 집계·비용 이력 정리 뒤에 안전 회로 검사를 호출한다.
앞선 단계가 예외로 종료하면 해당 회차의 마지막 안전 검사가 실행되지 않는다.
삭제 처리 일부는 비용 집계 전에 실행되므로 모든 삭제 작업이 건너뛰어진다고 표현하지 않는다.

**수정:** 집계 분리 설계에 포함된 검증된 비용 구간 판정과 기존 알림 상태를 연결한다.
필수 안전 검사는 외부 통계 조회보다 먼저 실행하고, 외부 통계/알림 실패가 이를 막지 않게 한다.
알림은 상태 변화와 정해진 재알림 간격에만 보낸다. 현재 승인된 발신 설정을 재사용하며
새 자격 증명이나 발신자를 임의 생성하지 않는다.

**완료 기준:** 통계 실패에도 필수 검사가 수행되고, 비용 경계/불완전 데이터/중복 평가가
검증된다. 알림은 실제 발송·수신 확인 전에는 완료로 보고하지 않는다.

## 5. 사용자에게 보이는 설명과 실제 동작의 불일치 — P2

- 압축: `image-compress-workbench.tsx`는 `location`을 server로 유지한 채 정책에 따라
  실제 실행을 local로 바꾼다. 전환 안내는 존재하지만 서버 라디오 선택 표시가 남을 수 있다.
  실제 선택 가능한 처리 방식과 표시를 일치시키고, 로컬이 서버와 동일한 압축 성능을 보장하지
  않는다는 차이를 짧게 안내한다. 서버 복구 시 로컬 선택에서 묵시적으로 업로드하지 않는다.
- 개인정보 흐림: 공개 페이지와 `tool-implementations.ts`·카탈로그에는 얼굴·번호판·이름을
  자동 탐지하는 것으로 읽히는 문장이 있다. 구현은 선택적인 브라우저 `FaceDetector`와
  수동 영역 선택이며 번호판/OCR 탐지기는 없다. “지원 브라우저에서 얼굴 자동 찾기,
  번호판·이름은 직접 영역 지정”으로 정정한다. 이를 위해 새 AI 모델을 도입할 필요는 없다.
- 수동 흐림 영역 지정은 pointer down/up만 구현되어 있다. 키보드로 영역을 추가/조정하는
  조작을 제공하고 실제 키보드 완료 흐름을 CI에서 검증한다. 자동 탐지가 없는 환경에서
  키보드만으로 작업을 끝낼 수 있는지도 포함한다.

**완료 기준:** 정책 server/local/실패 상태에 따라 처리 방식·실행 문구·전송 고지가 일치하고,
수동·자동 탐지 설명이 기능과 일치한다. 키보드로 영역 지정부터 저장까지 완료할 수 있다.

## 6. 검증 통과와 서비스 완료의 구분 — P2

이번 기존 테스트는 8개 파일·54개가 통과했지만 위 확대 결함을 잡지 못했다.
현재 테스트는 일부 유틸리티와 계약을 검증하고 실제 추가 도구 흐름의 중요한 분기는 빠져 있다.
테스트 개수보다 재현된 결함과 실제 결과를 검사하는 소수 회귀 테스트를 추가해야 한다.

`/health?requireJobs=1`은 설정 플래그만 본다. 현재 운영 모니터는 이미 `/v1/policy`도
검사하므로 중복 모니터를 만들지 않는다. 다음을 구분해 기존 운영 결과에 표시한다:
페이지 접근 가능 / 일반 사용자 서버 작업 허용 / 실제 작업 완료 / 집계 정상 / 삭제 확인.
보호된 기존 canary·공개 검증 절차를 사용하며, 매 모니터마다 무제한 실작업을 생성하지 않는다.

또한 일반 `pnpm verify`에는 Docker 기반 네이티브 준비와 60초 fuzz 검사가 포함된다.
설명보다 실제 기본 검증 비용이 크다. 변경 경로에 맞는 빠른 검증 명령을 명시하고,
릴리스 후보에는 기존 필수 보안·통합·품질 검증을 그대로 유지한다.

## 실행 순서와 범위

1. 추가 도구의 입력/출력 제한과 확대 대체 경로 결함을 작은 수정으로 처리한다.
   설명·키보드 조작 문제도 기존 화면 안에서 고친다. 완료 기준은 회귀 테스트와 CI 실제 산출물이다.
2. 승인된 집계 분리 작업을 끝까지 수행하고 현재 운영 상태를 재확인해 서버 압축을 복구한다.
   서비스 성공은 실제 결과와 삭제까지 검증한다. 진단 도구만 늘리는 작업으로 끝내지 않는다.
3. 엔진 갱신·코덱 비교는 별도 변경으로 한다. 현행 엔진을 기준으로 같은 입력·같은 출력 형식·
   유사한 지각 품질에서 크기, 처리시간 P50/P95, 최대 메모리와 실패율을 비교한다.
   서버 이용 불가 문제를 엔진 실험의 완료까지 미루지 않는다.
4. 복구 후 실제 완료율·다운로드 요청·수동 조치 횟수를 확인한다. 광고 연결은 별도 준비 상태이며
   계정/게시자 ID/운영자의 필요한 절차 확인 없이 활성화하지 않는다.

```bash
pnpm exec vitest run tests/check-production-health.test.ts \
  apps/api-worker/src/cost-accounting-runtime.test.ts \
  apps/api-worker/src/cost-accounting-scheduler.test.ts \
  apps/api-worker/src/sweeper.test.ts \
  apps/web/src/lib/image-compress-presentation.test.ts \
  apps/web/src/lib/local-image-optimize-fallback.test.ts \
  apps/web/src/lib/image-extra.test.ts tests/tool-catalog-routes.test.ts --maxWorkers=2
```

8개 파일·54개 통과. 확대 함수 재현은 실제 소스에서 `fitDimensions`와 `loadRenderSource`를
추출해 설치된 TypeScript로 변환하고 Node VM에서 호출했다. 큰 이미지나 버퍼는 만들지 않았다.
HTTP 조사는 Node fetch 경로로 수행했다. Python urllib의 초기 조회는 403이었으므로
그 결과만으로 사이트 장애나 크롤러 차단을 단정하지 않았다.
전체 검증·침투 검사·모바일 실기기 검증·엔진 간 새 벤치마크는 수행하지 않았다.
