# 서비스 복구 변경과 운영 차단 조건

기준: 2026-10-06 한국 시간. 이 문서는 구현 검증과 실제 운영 복구를 구분한다.

## 수정한 문제

- 외부 통계 조회 장애는 별도 집계 경고로 기록한다. 파일 삭제 지연, 증명 충돌, 잘못된 내부 상태 등 실제 안전 문제는 계속 작업을 차단한다.
- 확정된 연속 24시간 비용만 비용 상한 판정에 사용한다. 누락된 비용을 0원으로 처리하지 않는다.
- 경고 메일의 중복·재시도를 제한하고 미발송 상태를 운영 진단에 표시한다. 기존 처리량·시간·메모리 한도는 올리지 않았다.
- 과거 미확정 시간을 새 집계 기간으로 전환할 때 숨기지 않는다. 검증되지 않은 안전 이력은 보존하며, 되돌리기가 새 사고를 덮어쓰지 않는다.
- 확대 전 입력·출력 크기와 합계 메모리를 검사하고, 실제 2배/4배 출력 또는 명확한 실패를 보장한다. GIF 첫 프레임 변환은 제한 내에서 유지한다.
- 수동 흐림 영역을 키보드로 조절할 수 있다. 자동 탐지 설명과 서버 불가 시 로컬 선택 표시를 고쳤다.
- Next.js를 16.3.5에서 보안 수정 버전 16.3.6으로 갱신하고 라이선스 고지를 재생성했다.

## 확인한 검증

- 전체 단위 테스트: 195개 파일, 2,629개 테스트 통과.
- 전체 검사 이후 D1 변경 건수 표시 수정의 관련 회귀 테스트 64개도 통과했다.
- 실제 Worker/D1 통합 테스트: 22개 파일, 185개 테스트 통과.
- 최종 `pnpm verify` 전체 통과: 웹·서버 빌드, 정적 페이지·검색 유입 번들 및 60초/214건 엔진 비정상 입력 검증 포함.
- 운영 의존성 보안 검사: 알려진 취약점 0건.
- 독립 코드 검토의 배포 순서·집계 상태·이력 보존 지적을 수정하고 회귀 테스트로 검증했다.
- libvips 경계 검사 수정 후 네이티브 재빌드 및 60초 비정상 입력 검증: 216건 통과(제한 초과·지원하지 않는 입력 200건 거부, 유효 입력 16건 처리). 소스·패치·실행 파일 증명과 관련된 72개 테스트도 통과했다.
- GitHub 브라우저 검증은 492개 통과, 15개 실패, 33개 제외로 종료됐다. 실패는 모두 확대 선택 항목의 정확한 이름을 찾지 못한 경우다. 명시적인 접근성 이름을 추가했으며 재검증이 필요하다. 로컬 Playwright는 실행하지 않았다.

## 아직 운영을 재개하지 않은 이유

1. **libvips 실제 경계 검사 누락을 수정했으나 릴리스 검증·승인이 남았다.** 기존 판단은 수정 커밋 포함 여부와 메모리 매핑 경로만 확인했다. 검사를 넓히자 8.18.7 실행 파일의 `sniff_at_most` 경로는 과도한 길이에서도 읽기를 호출했다. 후속 upstream 변경이 오류 반환을 릴리스 빌드에서 제거되는 assertion으로 바꾼 탓이다. 원래 오류 반환 검사를 복원하고, 같은 검사로 수정 전 실패·재빌드 후 두 경로 통과를 확인했다. 원격 악용 가능성을 입증한 것은 아니다. 버전과 원본 HIGH 검출은 유지한다. 커밋된 소스로 CI가 만드는 정확한 릴리스 이미지의 새 검사 및 기존 절차에 따른 해당 이미지 보안 검토·승인이 필요하다. [수정 근거와 검증 범위](2026-10-05-libvips-source-bounds-repair.md)를 참조한다.
2. **과거 안전 기록 부족과 별도 승인 복구.** 기존 서버는 집계 오류가 먼저 기록되면 뒤의 안전 사고 사유를 가릴 수 있었다. 보존된 순간별 진단만으로 그 사이에 사고가 없었다고 증명할 수 없다. 새 마이그레이션은 이력 시작을 임의로 소급하지 않고 `0`(미확인)으로 둔다. 검증된 연속 기록 없이 기존 차단을 자동 해제하지 않는다. 별도 수동 복구 경로는 새 서버의 빈 작업·저장소 확인, 기존 한도 유지, 단 한 번의 승인 기록 및 실패 시 재차단을 구현했다. 운영자가 과거 안전·비용·늦은 저장 요청의 불확실성을 명시적으로 수락해야 실행할 수 있다. [구체적인 복구 제안](../deployment/processing-legacy-recovery.md)은 구현했지만 실행하지 않았다.
3. **메일 전달 미검증.** `ALERT_EMAIL` 바인딩 외에 검증된 발신·수신 주소가 필요하다. 설정 또는 전달 증명이 없으면 `alertPending`을 남긴다. 실제 메일을 발송하지 않았다.

릴리스는 기존 보호 절차인 main CI → staging → 승인된 production canary → 정확한 산출물 공개 승격을 따른다. 현재 변경은 이 절차나 보안 증명 조건을 우회하지 않는다. 실제 업로드 → 압축 → 다운로드 → 삭제 성공과 공개 정책 상태를 확인하기 전에는 서비스 정상화를 완료했다고 보고하지 않는다.
