# 집계 장애와 이미지 서버 작업 허용의 분리

상태: 방향 승인 후 작성한 설계안. 문서 검토 대기이며 구현·배포 승인이 아니다.

## 목표와 범위

무료 도구를 광고로 운영하고 수동 관리 부담을 줄인다는 제품 목표에 맞춰, 외부 사용량 통계가
일시적으로 없다는 이유만으로 이미지 압축을 중단하지 않는다. 서버 전송 고지, 로컬 처리 선택,
기존 처리량 제한과 안전 차단은 유지한다. PDF, 결제, 새 엔진, 새 토큰, 권한 확대는 범위 밖이다.

이 설계는 `2026-08-10-processing-public-admission-design.md`의 집계 미완료 시 일괄 차단
원칙을 대체하고, 설정만 있던 비용 판정·알림을 연결한다. 릴리스 증명·보안 검사·삭제 검증·
공개 승격 검증을 면제하지 않는다.

## 확인한 현재 상태

2026-10-05 로컬 기준 커밋은 `7867a35`다. 아래 내용은 코드 확인 결과이며 현재 프로덕션을
다시 조회했다는 뜻은 아니다. 이전의 Logpush 403 원인은 이 변경으로 해결되는 것이 아니다.

- `cost-accounting-runtime.ts`는 공급자 오류뿐 아니라 일부 내부 오류도 `incomplete`로 합친다.
- `cost-accounting-scheduler.ts`는 대상 시간 종료 후 1시간이 지나면 집계 확정 함수를 호출한다.
- `hourly-cost-sealer.ts`는 미완료를 `COST_ACCOUNTING_INCOMPLETE` 전역 차단으로 바꾼다.
- `d1-job-repository.ts`와 정책 응답은 전역 차단을 존중한다. 이 입장 제한 자체는 제거하지 않는다.
- 여러 차단 작성자가 최초 사유를 보존하므로, 뒤에 발생한 심각한 사유가 가려질 수 있다.
- D1 예약에는 계정·세션·네트워크별 일일 단위 한도, 대기 작업 수와 중복 요청 검사가 있다.
  실패·취소에도 최소 사용량이 정산된다. 컨테이너 수, 처리 시간과 자원 제한도 있다.
- 비용 상한은 설정·검증되지만 런타임 초과 판정으로 소비되는 경로는 확인되지 않았다.
  `operational_alert_state`와 이메일 바인딩도 있으나 발송 구현은 확인되지 않았다.
- 기존 `Production readiness monitor`는 공개 접근성을 검사한다. 집계 정상 여부나 메일 도착을
  증명하지 않는다.

## 선택한 접근

1. **집계 상태와 안전 차단 분리 — 선택.** 기존 예약·제한을 그대로 사용하고 공급자 조회 장애만
   별도 상태로 기록한다. 비용을 확인할 수 없는 기간에도 제한된 처리는 계속할 수 있다.
2. Logpush 복구만 계속 시도: 현재 오류가 해결돼도 같은 외부 의존성 장애에 다시 중단된다.
3. 전역 차단 무시: 삭제 실패나 데이터 불일치까지 통과시킬 수 있으므로 사용하지 않는다.

## 동작 계약

| 상황 | 신규 서버 작업 | 집계 및 알림 |
| --- | --- | --- |
| 공급자 HTTP 오류·시간 초과·정상 형식의 미완료/표본 데이터 | 기존 제한 안에서 허용 | 미확정으로 기록, 제한된 재시도와 알림 |
| 모든 필수 증거가 검증된 시간 | 기존 제한 안에서 허용 | 해당 시간만 확정, 복구 여부 갱신 |
| D1 상태 손상·릴리스 증명 불일치·로그 위변조/충돌 | 차단 | 안전 사고로 기록 |
| 삭제 지연·결과 검증 실패·비정상 대기열 | 차단 | 기존 안전 절차 유지 |
| 처리량·대기 작업 수 한도 초과 | 해당 요청 거부 | 기존 정책 및 로컬 선택 유지 |
| 검증 가능한 비용 상한 초과 | 차단 | 실제 근거와 적용한 상한 기록 |
| 알림 전송 실패 | 그 자체로 압축을 차단하지 않음 | 미발송 상태 유지, 재시도 |

이 표의 '허용'은 공개 비율, 활성 릴리스 증명, 업로드 검증, 모든 기존 제한을 통과한다는 전제다.
누락·손상된 내부 상태를 '공급자 장애'로 분류하는 포괄적 예외 처리는 금지한다.

## 최소 구조 변경

### 1. 집계 상태

`rollout_control.circuit_open`은 안전 차단으로 남긴다. 별도의 단일 행 집계 상태에 현재 epoch,
`unknown | degraded | healthy`, 고정된 사유 코드, 마지막 평가 시각과 미완료 대상 시간을 저장한다.
확정된 마지막 시간은 기존 `last_sealed_hour_key`를 사용하며 중복 저장하지 않는다.

모든 안전 차단 작성자는 기존 집계 미완료 사유보다 새로운 심각한 사유를 우선 기록해야 한다.
집계 상태 복구는 안전 회로를 닫지 않는다. 전환 중 새 위험이 발생하면 조건부 해제를 실패시켜야 한다.

- 새 상태는 `unknown`으로 시작하며 초기값을 정상으로 해석하지 않는다.
- 외부 조회 실패와 내부 증명/저장소 오류를 경계에서 구분한다. 외부 응답 본문은 저장하지 않는다.
- 외부 조회에 시간 제한을 두고 기존 5분 유지관리 주기를 사용한다. 별도 스케줄러는 만들지 않는다.
- 미완료가 대상 시간 종료 후 1시간을 넘으면 `degraded`로 기록한다. 전역 차단은 열지 않는다.
- 누락된 행과 형식이 깨진 행을 구분한다. 후자는 계속 안전 차단 대상이다.
- 누락 시간을 0원이나 `complete=1`로 채우지 않는다. 확정 커서·epoch를 건너뛰지 않는다.
- 과거 구간이 미완료라면 뒤의 조회 하나가 성공해도 `healthy`로 바꾸지 않는다.
- 미완료 이력으로 저장소가 무한히 커지지 않게 기존 보존 기한과 배치 크기를 적용한다.
  복구 불가능한 과거 공백은 미확정으로 남기며 삭제를 집계 완료의 증거로 사용하지 않는다.

### 2. 처리량 제한과 비용 판정

기존 D1 예약·정산, 실패 시 최소 단위 차감, 일일 한도, 재시도 상한, 요청 속도 제한,
단일 컨테이너와 처리 시간·메모리 제한을 그대로 재사용한다. 한도 수치도 올리지 않는다.

처리 단위는 달러가 아니며 클라우드 전체 청구 상한도 아니다. 고정 요금, 유휴 자원,
거부된 HTTP 요청과 공격 트래픽 비용까지 월 5달러 이하로 보장한다고 표현하지 않는다.

현재 설정만 있는 비용 판정은 기존 시간별 확정 비용과 상한에 연결한다. 새 가격 모델은 만들지 않는다.

- 동일 epoch·릴리스·모델의 연속된 최신 확정 24시간만 추정에 사용한다. 최신성은 마지막 시간 종료가
  평가 시각으로부터 2시간 이내인 것으로 정의한다. 조건 불충족은 비용 미확정이지 0원이 아니다.
- 24시간 비용 합계를 `C`, 같은 구간의 입장 건수를 `N`이라 한다. 월 추정은 `C × 30`,
  1,000건당 비용은 `ceil(C × 1000 / N)`이다. `N=0`이면 건당 값은 미정이며 월 추정만 평가한다.
  기존 시간별 비용에 포함된 고정비를 다시 더하지 않는다.
- 각 값이 기존의 대응 상한을 초과하면 안전 차단한다. 경계와 정수 오버플로를 검증하고
  동일 확정 구간을 여러 번 평가해도 결과를 중복 누적하지 않는다.
- 부분 데이터에서는 정상/비용 초과를 추정하지 않는다. 마지막 검증 결과와 집계 경고를 함께 유지한다.
  비용 차단이 이미 열려 있다면 통계 장애나 후속 정상값으로 자동 해제하지 않는다.
- 이 방식은 지연된 운영 비용 추정이지 청구서 또는 실시간 결제 차단이 아니다.

### 3. 유지관리와 알림

삭제·대기열·검증 안전 검사를 외부 통계 조회보다 먼저 실행한다. 통계 조회나 알림 실패가
후속 필수 안전 검사를 건너뛰게 하지 않는다. DB 또는 필수 안전 검사 실패를 무시하지 않는다.

기존 이메일 바인딩과 `operational_alert_state`를 사용해 작은 발송 경로만 연결한다.
`degraded` 진입, 지속 장애의 24시간 간격 재알림, 실제 복구 알림을 보낸다. 병렬 실행은
DB의 만료 가능한 발송 예약으로 중복을 제한하고 성공 후에만 전송 완료로 기록한다.
전송 후 DB 기록 실패에 따른 중복 가능성은 허용하며 정확히 한 번 전달을 주장하지 않는다.

내용은 환경, 사유 코드, 최초 미완료 시간과 확인 위치만 포함한다. 사용자 파일명·내용·토큰·
서명 URL은 포함하지 않는다. 발송 실패도 상태 조회와 기존 운영 점검에서 드러나게 한다.
기존 바인딩의 실제 발송·수신 검증 전에는 알림 완료라고 보고하지 않는다.

### 4. 사용자 정책과 운영 결과

브라우저에 공개하는 도구 계약과 전송 고지는 변경하지 않는다. 정책 응답과 실제 D1 예약의
허용 여부를 동일하게 유지한다. 운영 보고서는 `serviceAvailable`과 `accountingHealthy`를
구분한다. 전자는 참이고 후자는 거짓일 수 있으며 이를 모두 정상이라고 표시하지 않는다.

서버 한도 소진 시 기존 안내와 명시적 로컬 처리 선택을 유지한다. 새 관리자 화면은 만들지 않는다.

## 기존 차단의 전환과 배포

마이그레이션만으로 회로를 닫지 않는다. 과거의 최초 사유 문자열은 다른 위험이 없었다는 증거가 아니다.

1. 기존 배포 보호 환경과 직렬화 잠금 안에서 현재 Worker·릴리스·엔진·D1 상태를 다시 조회한다.
2. 신규 입장을 닫은 채 활성 작업과 outbox를 정리하고 삭제·대기열·검증·저장소 불변조건을 검사한다.
   보존된 오류·집계 충돌 이력도 검사한다. 자료 부족으로 다른 위험을 배제하지 못하면 해제하지 않는다.
3. 새 Worker와 가산적 스키마 변경을 기존 증명 경로로 배포한다. 임의 바인딩 수정이나 증명 위조는 없다.
   릴리스 절차상 새 epoch가 필요하면 이전 epoch의 공백과 비용·경고를 보존해 함께 보고한다.
   새 epoch가 생겼다는 사실만으로 집계를 정상 처리하거나 기존 안전 차단을 해제하지 않는다.
4. 기존 사유가 정확히 `COST_ACCOUNTING_INCOMPLETE`이고 나머지 검사가 통과한 경우에만,
   예상 활성 버전·epoch·차단 상태가 그대로인지 조건부 갱신으로 확인하면서 해당 차단을 해제한다.
   불일치·알 수 없는 사유·다른 안전 차단은 거부한다. 집계는 여전히 `degraded`로 남는다.
5. 관리자 canary로 업로드·압축·다운로드·삭제를 검증한 뒤 기존 공개 승격 경로를 사용한다.
   공개 검증에서 집계 정상 여부와 서비스 가능 여부를 별도로 보고한다.
6. 실패하면 신규 입장을 다시 닫고 이전 Worker를 복원한다. 기존 데이터와 집계 공백은 보존한다.

libvips 등 별도 공급망·릴리스 검사 실패는 이 설계로 우회하지 않는다. 새 보안 예외, 결제 변경,
토큰 생성·교체·삭제, Logpush 작업 생성은 이 작업에 포함하지 않는다.

## 검증 기준

- HTTP 403·시간 초과·표본 데이터에서도 집계만 `degraded`이며 적격 예약은 가능하다.
- 잘못된 공급자 데이터, 내부 증명 누락, D1 오류와 충돌은 단순 통계 장애로 삼키지 않는다.
- 통계 장애와 삭제/검증 실패가 함께 발생하면 안전 차단이 우선한다. 호출 순서를 바꿔도 동일하다.
- 병렬 예약, 중복 요청, 취소·실패·재시도와 날짜 경계에서 기존 단위·대기 수 제한이 유지된다.
- 미완료 시간이 0원/확정으로 변하지 않고, 오래된 공백·보존 처리 후에도 정상으로 오인되지 않는다.
- 비용 판정은 완전성·최신성·0건·경계값·정수 한계·중복 평가를 테스트한다.
- 알림 장애가 압축이나 안전 검사를 멈추지 않으며 발송 예약 만료 후 다시 시도된다.
- 전환 검사는 숨겨진 다른 위험, stale 버전/epoch, 활성 작업과 불완전한 증거를 거부한다.
- 정책 응답뿐 아니라 실제 처리·결과·삭제와 공개 접근을 확인해야 운영 복구로 판정한다.
- 로컬에서는 단위·D1 통합·타입·빌드를 검증한다. Playwright E2E는 GitHub Actions에서만 실행한다.

## 이번 단계의 산출물

이 문서만 작성한다. 문서 승인 후 구현 계획을 작성하고, 계획 검토와 실행 방식 선택 후 구현한다.
현재 프로덕션 상태·자격 증명·공개율은 변경하지 않는다.
