# PDF organizer workbench simplification design

**Date:** 2026-08-07
**Status:** Approved for implementation

## 목적

기존 PDF 페이지 정리 기능과 로컬 처리 경계는 유지하면서, 페이지 내용을 썸네일로 직접 확인하고
순서 변경·회전·삭제를 끝낸 뒤 결과를 바로 다운로드하는 단계별 단일 화면으로 바꾼다.

## 목표

- 파일 선택, 페이지 확인, 편집, 처리, 결과 중 현재 단계에 필요한 UI만 보여준다.
- 각 페이지를 저해상도 썸네일로 보여 사용자가 내용을 확인하며 편집할 수 있게 한다.
- 첫 페이지 정보를 확인하는 즉시 편집 화면을 보여주고 썸네일은 순차적으로 채운다.
- 썸네일과 최종 PDF는 모두 브라우저 안에서 만들며 파일을 네트워크로 보내지 않는다.
- 썸네일 생성과 해제의 메모리 상한을 명시하고 취소·파일 교체 때 즉시 정리한다.
- 모바일 320px, 키보드, 스크린 리더 사용성을 유지한다.
- 기존 PDF 정리 계약, 페이지 계획 함수, 분석 이벤트와 다운로드 방식을 재사용한다.

## 비목표

- PDF 정리 결과의 바이트, 파일명 또는 보존 정책 변경
- 페이지 내용 편집, 자르기, 복제, 여러 PDF 결합 또는 실행 취소 기록 추가
- 서버 업로드, 새 처리 API, 공유 버튼 또는 자동 다운로드 추가
- 드래그 전용 조작이나 새 외부 의존성 추가
- 다른 PDF 작업대 동시 변경

## 검토한 접근

1. **기존 3열 작업대를 CSS로 축소**: 변경은 작지만 파일·설정·빈 결과가 동시에 남고 페이지 내용도
   확인할 수 없다.
2. **단계별 화면과 페이지 번호 목록만 사용**: 처리 흐름은 단순해지지만 어떤 페이지를 옮기는지
   알아보기 어렵다.
3. **단계별 화면과 저해상도 썸네일 격자 사용**: 핵심 작업을 눈으로 확인할 수 있고 기존 편집·처리
   로직을 그대로 재사용할 수 있다. 이 접근을 선택한다.

## 사용자 흐름

### 1. 파일 선택

다음 요소만 보여준다.

- `PDF 페이지 정리`
- `PDF 선택` 기본 버튼과 드래그 앤 드롭 영역
- `PDF 1개 · 최대 50MB · 최대 500페이지`
- `파일은 이 기기에서만 처리돼요.`

파일을 선택하면 기존 PDF 검사로 형식, 페이지 수와 페이지 크기를 확인한다. 확인 중에는
`페이지 확인 중`과 `중단` 버튼만 보여준다.

### 2. 페이지 편집

검사가 끝나면 파일명, 원본 용량, 전체 페이지 수와 썸네일 카드 격자를 보여준다. 각 카드는 다음만
포함한다.

- 결과 순서
- 페이지 썸네일 또는 생성 중 자리표시자
- `원본 {n}페이지`와 회전 각도
- 위로 이동, 아래로 이동, 시계 방향 90도 회전, 삭제 버튼

모바일은 2열, 넓은 화면은 공간에 맞는 자동 열 수를 사용한다. 버튼은 드래그 없이도 모든 작업을
완료할 수 있어야 한다. 포인터 사용자는 카드를 드래그해 순서를 바꿀 수 있지만, 드래그는 기존
페이지 이동 함수를 호출하는 보조 입력 방식일 뿐 별도 상태를 만들지 않는다.

격자 위에는 `PDF 교체`와 `초기화`, 아래에는 `{n}페이지로 PDF 만들기` 기본 버튼만 둔다. 기존 영문
장식 문구, 3열 패널, 별도 설정 패널, 빈 결과 패널, 중복 상태와 모바일 고정 작업 바는 제거한다.

### 3. 처리

처리 중에는 다음만 보여준다.

- `PDF 정리하는 중`
- 기존 Worker 이벤트의 단계 문구와 실제 진행률
- `중단`

썸네일 격자와 편집 버튼은 숨기되 페이지 계획은 유지한다. 취소하면 같은 편집 화면으로 돌아간다.

### 4. 결과

성공하면 다음 순서로 보여준다.

- `페이지 정리 완료`
- `원본 {n}페이지 → 결과 {m}페이지`
- 결과 용량
- `PDF 다운로드 ↓` 기본 버튼
- 전자서명·북마크·양식 보존 경고가 있을 때만 짧은 안내
- `다른 PDF 정리` 보조 버튼

처리 시간, 반복 설정, 공유 버튼과 자동 다운로드는 표시하지 않는다.

## 화면 상태와 데이터 흐름

화면은 기존 상태에서 파생한 다섯 단계 중 하나만 렌더링한다.

1. `select`: 정상 검사된 파일이 없음
2. `inspecting`: PDF 구조와 페이지 정보를 확인 중
3. `editing`: 페이지 계획이 준비됨
4. `processing`: 정리 Worker 실행 중
5. `result`: 결과와 다운로드 URL 준비됨

별도 전역 상태나 범용 상태 머신은 추가하지 않는다. 기존 `items`, `pagePlan`, `inspecting`,
`processing`, `progress`, `result`와 정리 함수를 유지한다. `createPdfPagePlan`, `movePdfPage`,
`rotatePdfPage`, `removePdfPage`, `runPdfJob`과 `pdf.organize@1` 계약은 변경하지 않는다.

썸네일은 최종 PDF 처리와 분리된 `pdf.thumbnail@1` 브라우저 계약으로 생성한다. 전용 Worker가 기존
PDF raster runtime을 재사용해 문서를 한 번 열고, 원본 순서대로 한 페이지씩 렌더링한다. 각 썸네일은
긴 변 최대 160px, 불투명 흰 배경의 WebP로 인코딩해 전송한다. 한 번에 캔버스 하나만 할당하고 다음
페이지로 넘어가기 전에 페이지와 캔버스를 해제한다. 썸네일 이벤트에는 작업 ID, 원본 페이지 번호,
MIME과 바이트만 포함하며 파일명이나 object URL을 포함하지 않는다.

UI는 수신한 바이트로 object URL을 만들고 원본 페이지 번호에 연결한다. 회전은 썸네일을 다시 만들지
않고 카드 이미지의 CSS 변환과 접근 가능한 회전 문구로 반영한다. 이동·삭제도 기존 `pagePlan`만
바꾼다. 파일 교체, 새 작업, 취소와 unmount 때 Worker를 종료하고 모든 썸네일·결과 object URL을
해제한다.

최대 500페이지에서도 썸네일 원시 캔버스 예산은 한 장으로 제한되고, 각 전송 바이트는 160px 캔버스의
원시 RGBA 크기를 넘지 않게 검증한다. 누적 썸네일 바이트가 48MiB에 도달하면 나머지 카드는 페이지
번호 자리표시자를 유지하며 `일부 미리보기는 메모리를 위해 생략했어요.`라고 한 번만 알린다. 편집과
최종 결과 생성은 계속 사용할 수 있다.

## 오류와 복구

- 형식, 크기, 페이지 수, 손상·암호화 오류는 선택 단계에서 짧게 표시하고 다시 선택할 수 있게 한다.
- 개별 썸네일 생성 실패는 해당 카드만 페이지 번호 자리표시자로 남기며 다른 썸네일과 편집을 계속한다.
- Worker 시작 실패나 메모리 한도 도달은 페이지 번호 편집으로 안전하게 낮추고 최종 정리는 막지 않는다.
- 검사 취소는 파일 선택 단계, 처리 취소는 같은 편집 단계로 돌아간다.
- 마지막 한 페이지의 삭제는 계속 막는다.
- 다운로드 시작 실패는 결과와 다운로드 버튼을 유지해 다시 누를 수 있게 한다.
- 파일명, 파일 내용, 썸네일 바이트와 object URL은 로그나 네트워크에 기록하지 않는다.

## 접근성과 반응형

- 단계가 바뀔 때 단계 제목에 프로그램적으로 초점을 옮긴다.
- 검사·처리 진행과 오류는 하나의 `aria-live` 영역에서만 알린다.
- 썸네일은 장식 이미지로 두고 카드의 원본 페이지·결과 순서·회전 상태를 텍스트로 제공한다.
- 이동·회전·삭제는 설명 가능한 native button을 사용하고 최소 44px 터치 영역을 유지한다.
- 키보드 초점 순서는 결과 순서와 같으며 이동 후 해당 카드의 대응 버튼에 초점을 유지한다.
- 포인터 드래그에는 동일한 키보드 버튼 대안을 제공하고 드롭 위치를 시각·텍스트로 알린다.
- 320px에서는 2열을 유지하되 카드와 버튼이 화면 밖으로 넘치지 않고 가로 스크롤이 생기지 않게 한다.
- 색상 없이도 선택, 이동 위치, 회전과 삭제 불가 상태를 이해할 수 있게 한다.

## 검증

기존 순수 페이지 계획 및 PDF 파이프라인 테스트를 유지하면서 다음을 추가한다.

- 썸네일 계약 검증, 페이지 순서, MIME 서명, 긴 변 160px 이하와 바이트 상한
- PDF를 한 번만 열고 한 페이지·한 캔버스씩 처리하며 성공·실패·취소 때 자원을 해제함
- 썸네일이 순차적으로 나타나고 실패한 카드만 자리표시자로 낮아짐
- 이동·회전·삭제·초기화 후 썸네일과 텍스트 순서가 같은 페이지 계획을 가리킴
- 버튼과 포인터 드래그가 동일한 페이지 계획 결과를 만듦
- 처리 취소 후 편집 상태 복구, 결과 다운로드 재시도, 파일 교체와 unmount URL 해제
- 48MiB 썸네일 예산에서 안전하게 중단하고 최종 PDF 정리는 계속 가능함
- 파일 내용, 파일명, 썸네일과 object URL이 기기 밖으로 나가지 않음
- Chromium, Firefox, WebKit, 모바일 프로필과 320px 레이아웃

브라우저 썸네일은 바이트 동일성을 요구하지 않는다. 원본 페이지 수, 이미지 MIME, 크기 상한과 페이지
식별을 검증한다. 최종 PDF는 기존처럼 페이지 순서, 회전, 삭제 결과, MIME 서명과 경고를 검증한다.

## 완료 기준

- 사용자가 페이지 내용을 보며 순서 변경·회전·삭제를 완료할 수 있다.
- 각 단계에서 현재 필요한 주 행동 하나만 분명하게 보인다.
- 첫 페이지 정보 확인 후 편집 화면이 나타나고 썸네일은 정직한 진행 상태로 채워진다.
- 최대 입력에서도 썸네일 메모리 상한과 모든 취소·정리 경로가 검증된다.
- 최종 PDF 결과와 개인정보 경계는 기존과 동일하다.
- 전체 `pnpm verify:all`이 통과한다.
