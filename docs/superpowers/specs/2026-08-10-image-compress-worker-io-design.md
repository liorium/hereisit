# 이미지 압축 UI 파일 I/O Worker 설계

## 목표

이미지 압축 화면에 남아 있는 원본 파일 전체 읽기와 무손실 메타데이터 처리를 UI 영역에서 제거한다. 파일 선택 검사는 압축 전용 Worker가 수행하고, 스마트 압축은 기존 `image.pipeline@2` Worker를 재사용하며, 무손실 압축은 압축 전용 Worker가 처리한다.

화면, 한국어 문구, 서버 처리 정책, 압축 결과, 다운로드 동작과 공개 `image.optimize@1` 계약은 바꾸지 않는다. 성공 기준은 제품 UI 코드인 `image-compress-workbench.tsx`와 로컬 압축 조정 코드가 원본 `File.arrayBuffer()`를 호출하거나 전체 원본 바이트를 보관하지 않는 것이다.

## 현재 흐름과 문제

현재 압축 화면은 파일을 선택할 때 각 파일 전체를 UI 영역에서 읽고 형식, 크기와 애니메이션 여부를 검사한다. 로컬 처리에서도 `runLocalImageOptimizeFallback()`이 같은 파일을 다시 UI 영역에서 읽는다.

- 최대 20개, 파일당 30MiB 원본의 버퍼 할당과 헤더 검사가 UI 영역에서 순차 실행된다.
- 스마트 압축은 UI 검사 읽기 뒤 기존 공통 이미지 Worker가 파일을 다시 읽는다.
- 무손실 압축은 JPEG 방향·ICC와 PNG iCCP 검사 및 메타데이터 제거까지 UI 영역에서 실행한다.
- 파일 선택 중 새 선택 또는 화면 이탈이 발생해도 현재 읽기를 직접 격리할 Worker 수명주기가 없다.

직전 작업으로 공통 이미지 배치와 이미지 워터마크의 전체 파일 읽기는 Worker가 소유한다. 이번 작업은 아키텍처 문서에 명시된 이미지 압축의 마지막 두 UI 전체 읽기를 제거한다.

## 검토한 접근

### 1. 압축 전용 Worker와 기존 공통 Worker 조합 — 선택

압축 전용 Worker는 파일 선택 검사와 무손실 메타데이터 정리만 담당한다. 스마트 압축은 검증된 기존 `runImageBatch()`에 파일을 직접 전달한다. 압축 프리셋이 한 배치에서 동일하므로 파일 선택과 무손실 배치마다 Worker 하나를 순차 재사용해 시작 비용과 최대 메모리를 함께 제한할 수 있다.

### 2. `image.pipeline@2` Worker에 압축 전용 요청 추가

Worker 파일 수는 줄지만 공통 크기 조절·변환 계약에 `image.optimize@1`의 검사와 무손실 서버 대체 판단이 섞인다. 버전, 오류와 취소 의미가 결합되므로 선택하지 않는다.

### 3. UI에서 파일 접두사만 읽기

할당량은 줄지만 큰 JPEG 메타데이터 뒤의 치수 정보와 HEIC 박스 구조를 완전히 검사하지 못할 수 있다. 지원하던 정상 파일을 거부할 수 있고 UI 읽기도 남으므로 선택하지 않는다.

## 구성요소와 책임

### 압축 전용 Worker

`packages/browser-runtime/src/image-optimize.worker.ts`는 프로토콜 `1`의 내부 요청 두 종류를 처리한다.

- `inspect`: 네이티브 `File`을 읽고 기존 `inspectImageHeader()` 결과인 MIME, 너비, 높이와 애니메이션 여부를 반환한다. 선택 화면은 이 결과에 기존 HEIC·애니메이션·40,000,000픽셀 제외 정책과 문구를 그대로 적용한다.
- `lossless`: 같은 검사를 수행한 뒤 기존 JPEG 방향·ICC 및 PNG iCCP 정책을 적용하고, 가능한 JPG·PNG만 기존 `stripJpegMetadata()` 또는 `stripPngMetadata()`로 정리한다.

Worker는 한 번에 작업 하나만 처리한다. 취소되거나 새 배치가 폐기되면 UI 런너가 Worker를 종료하고 늦은 이벤트를 무시한다. 파일 내용, 이름, 썸네일, 객체 URL과 결과 URL을 기록하지 않는다.

### 압축 Worker 배치 런너

`packages/browser-runtime/src/run-image-optimize-batch.ts`는 두 공개 로컬 API를 제공한다.

- 파일 선택 검사 배치: 입력 순서를 보존하고 항목별 검사 결과 또는 안전한 오류를 반환한다.
- 무손실 압축 배치: 입력 순서를 보존하고 기존 `LocalImageOptimizeResult` 의미와 진행 이벤트를 반환한다.

각 배치는 Worker 하나를 생성해 파일을 순차 처리한다. 최대 동시 전체 원본 읽기는 한 개다. 런너는 내부 작업 ID, 메시지 정확한 키, 이벤트 순서, 결과 버퍼와 길이를 검증하고 배치 취소 시 아직 시작하지 않은 항목도 한 번만 취소 정산한다.

### 스마트 압축 조정

스마트 로컬 압축은 파일 선택 Worker가 확인한 MIME으로 기존 파이프라인 설정을 만들고 `runImageBatch()`에 전체 배치를 동시성 `1`로 전달한다. 공통 Worker는 원본 바이트를 다시 구조적으로 검사하므로 선택 결과를 보안 경계로 신뢰하지 않는다. 기존 `NO_SIZE_REDUCTION` 원본 유지와 PNG 무손실 대체 경고를 그대로 매핑한다.

### 압축 화면

`image-compress-workbench.tsx`는 선택한 파일을 한 검사 배치에 전달하고 진행 문구를 기존처럼 갱신한다. 새 선택, 취소와 언마운트는 활성 검사 또는 처리 배치를 종료한다. 사용자 설정, 결과 요약, 다운로드와 서버 업로드 고지는 바꾸지 않는다.

기존 `local-image-optimize-fallback.ts`의 UI 바이트 처리 책임은 제거한다. 결과 매핑이 작게 남을 필요가 있으면 파일 바이트를 읽지 않는 조정 함수만 유지하고, 그렇지 않으면 삭제한다.

## 내부 계약과 신뢰 경계

모든 Worker 파일 입력은 기존 공통 `{ name, mimeHint, byteLength, file }` 봉투와 네이티브 `File`을 사용한다. 요청과 이벤트는 `protocol: 1`, 안전한 내부 작업 ID와 정확한 열거 가능 문자열 키를 요구한다.

Worker는 다음 순서로 검증한다.

1. 메시지 종류, 프로토콜, 작업 ID와 정확한 키
2. 네이티브 `File` 여부와 봉투 이름·MIME·크기의 실제 파일 일치
3. 1바이트 이상 30MiB 이하의 입력 한도
4. `File.arrayBuffer()`가 반환한 일반 `ArrayBuffer`와 실제 길이
5. 기존 이미지 헤더 구조와 지원 형식 정책. `lossless`는 40,000,000픽셀 한도도 적용하고, `inspect`는 치수를 반환해 선택 화면의 기존 정책이 판정한다.
6. 무손실 결과의 일반 `ArrayBuffer`, MIME, 크기와 치수

잘못된 봉투는 `INVALID_SPEC`, 입력 크기 위반은 `MEMORY_LIMIT`, 읽기 실패·길이 불일치·손상 이미지는 공개된 짧은 입력 오류로 반환한다. 무손실 WebP, 회전이 필요한 JPEG, ICC가 있는 JPEG와 PNG는 기존처럼 `LOSSLESS_SERVER_REQUIRED`로 남긴다. 알 수 없는 예외의 원문은 UI에 노출하지 않는다.

## 유지할 한도와 동작

- 공개 도구 계약 `image.optimize@1`
- 파일 최대 20개, 파일당 30MiB, 이미지당 40,000,000픽셀
- JPG·PNG·WebP 지원과 HEIC·HEIF 같은 형식 압축 제외
- 애니메이션 이미지 제외
- 스마트 프리셋 품질, 최소 절감률, 원본 유지, PNG 경고
- 무손실 JPG·PNG 메타데이터 정책과 서버 필요 판단
- 서버 정책 재확인, 업로드 고지, 재시도 가능한 서버 실패의 로컬 대체
- 결과 크기·형식·파일명·다운로드 전용 UX
- 로컬 처리 중 파일 네트워크 전송 없음
- 새 의존성, 코덱, UI 또는 공개 진행 단계 없음

## 취소와 오류 처리

- 검사 중 새 파일을 선택하면 이전 검사 Worker를 종료하고 이전 결과를 반영하지 않는다.
- 처리 취소 또는 언마운트 시 스마트 배치와 무손실 Worker 배치를 모두 종료한다.
- Worker가 읽는 중 종료돼도 늦은 완료·진행 이벤트와 다운로드 결과를 만들지 않는다.
- 한 파일의 정상적인 형식 오류는 그 항목만 거부하고 다음 항목을 검사한다.
- 잘못된 Worker 이벤트나 결과 버퍼는 해당 항목을 안전한 Worker 오류로 끝내고 Worker를 교체하거나 배치를 종료한다.
- UI 관찰자 예외는 처리 결과를 소유하지 않는다.

## React 성능 원칙

- 파일 바이트와 고빈도 진행 상태는 React 렌더 상태에 보관하지 않는다.
- 활성 배치 핸들은 `ref`로 보관하고 렌더링에 필요한 항목 상태만 갱신한다.
- 독립 파일의 상태 갱신은 기존 함수형 `setItems()`를 유지한다.
- 무거운 이미지 검사·메타데이터 코드는 Worker 청크에 남기고 화면 청크로 다시 가져오지 않는다.
- 새 전역 이벤트 리스너나 외부 상태 관리 의존성을 추가하지 않는다.

## 검증

### Worker와 런너 단위 테스트

- 제품 UI 영역의 `File.arrayBuffer()` 감시가 호출되지 않음
- 한 Worker가 여러 선택 파일을 순서대로 읽고 결과 순서를 보존함
- 무손실 JPG·PNG가 기존과 같은 결과와 치수를 반환함
- WebP, 회전 JPEG, ICC JPEG·PNG가 기존 서버 필요 결과를 유지함
- 파일 봉투 위조, 비네이티브 파일, 읽기 실패, 잘못된 버퍼와 길이를 거부함
- 새 선택·처리 취소 뒤 늦은 이벤트를 무시하고 한 번만 정산함
- 결과 바이트만 전송 목록으로 UI에 반환함

### 웹 통합 테스트

- 파일 선택이 Worker 검사 결과로 동일한 준비·제외 상태를 만듦
- 스마트 배치가 기존 공통 Worker를 사용하고 원본 유지와 PNG 경고를 보존함
- 무손실 배치가 전용 Worker 결과를 동일한 UI 결과로 매핑함
- 서버 경로와 재시도 가능한 실패의 로컬 대체가 유지됨
- 브라우저 Worker 대역이 새 네이티브 `File` 계약을 실제 형태로 처리함

### 전체 검증

- 집중 Vitest RED → GREEN 기록
- `pnpm verify`
- 보호된 GitHub Actions에서 Chromium, Firefox, WebKit과 모바일 3종 및 제품 분석 통과
- Cloudflare Pages와 처리 스테이징 배포 성공

## 완료 기준

- `image-compress-workbench.tsx`와 로컬 압축 조정 코드에 원본 `File.arrayBuffer()` 호출이 없음
- 파일 선택 검사와 무손실 메타데이터 처리를 Worker가 소유함
- 스마트 압축은 기존 공통 Worker에서 원본 파일을 읽고 처리함
- 화면, 결과, 오류 의미, 서버 대체와 다운로드 UX가 유지됨
- 단위·통합·퍼즈·빌드·6개 브라우저 CI가 통과함
- 병합 후 Pages와 처리 스테이징 배포가 성공함
- 이번 작업의 임시 파일, worktree, Docker 이미지와 빌드 캐시가 정리됨

## 제외 범위

- 이미지 인코더·코덱·품질·압축률 정책 변경
- 서버 이미지 엔진 또는 처리 비율 변경
- UI 재설계와 새 사용자 기능
- Worker 동시성 확대
- 브라우저 내부 `File` 구조화 복제 구현 방식에 대한 무복사 보장

브라우저가 `File` 데이터를 내부적으로 복사하는지는 보장하지 않는다. 제품 코드가 UI 영역에 전체 원본 `ArrayBuffer`를 만들거나 보관하지 않는 구조를 보장한다.
