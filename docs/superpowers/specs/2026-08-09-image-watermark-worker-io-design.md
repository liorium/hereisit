# 이미지 워터마크 Worker 파일 I/O 개선 설계

## 목표

이미지 워터마크 배치에서 원본 이미지와 로고 파일 읽기를 Worker가 소유하도록 바꾼다. 메인 UI 영역의 큰 `ArrayBuffer` 할당과 동시 파일 읽기를 제거해 모바일과 대용량 배치의 반응성과 메모리 안정성을 높인다.

이 작업은 워터마크 합성·인코딩 알고리즘이나 결과 화질을 바꾸지 않는다. 전체 처리 시간이 크게 줄어든다고 가정하지 않으며, 주된 성공 기준은 UI 영역에서 파일 바이트를 읽지 않는 것과 기존 결과·오류·취소 동작을 보존하는 것이다.

## 현재 흐름과 문제

현재 `runImageWatermarkBatch()`가 각 `File.arrayBuffer()`를 호출하고 결과 버퍼를 Worker로 전송한다. 로고도 메인 영역에서 한 번 읽은 뒤 보관하고 Worker마다 복사한다.

전송 시 원본 버퍼는 분리되므로 장기 중복 보관은 제한되지만 다음 비용은 남는다.

- 최대 50MB 원본 파일 읽기와 버퍼 할당이 메인 UI 영역에서 일어난다.
- 두 Worker가 동작하면 메인 영역이 여러 파일 읽기와 Worker 상태 관리를 함께 담당한다.
- 최대 10MB 로고 버퍼를 메인 영역에 보관하고 Worker마다 복사한다.
- 파일 읽기 실패와 Worker 처리 실패가 서로 다른 영역에서 처리돼 상태 기계가 복잡하다.

## 선택한 접근

배치 실행기는 검증된 파일 메타데이터와 네이티브 `File`을 구조화 복제로 Worker에 보낸다. Worker가 파일을 읽고 바이트 길이를 다시 검증한 뒤 기존 이미지 워터마크 파이프라인에 전달한다.

브라우저가 `File`의 파일 데이터를 메시지 전송 시 즉시 복사한다고 가정하지 않는다. 성능상 보장하는 것은 메인 코드가 `arrayBuffer()`를 호출하거나 원본 바이트 버퍼를 보관하지 않는다는 구조적 경계다.

## 데이터 흐름

1. UI가 기존 공개 배치 계약대로 원본 `File`, 항목 ID, 워터마크 설정을 전달한다.
2. 배치 실행기가 항목 수, 파일 크기 합계, 설정, 파일 이름·MIME·크기를 동기 검증한다.
3. 배치 실행기가 `{ name, mimeHint, byteLength, file }` 입력 봉투를 유휴 Worker에 전달한다.
4. Worker가 봉투의 정확한 키와 네이티브 `File`을 검증하고, 봉투 메타데이터가 `File`의 이름·MIME·크기와 일치하는지 확인한다.
5. Worker가 `File.arrayBuffer()`를 호출하고 반환값이 일반 `ArrayBuffer`이며 선언된 크기와 일치하는지 확인한다.
6. Worker가 기존 헤더 검사, 디코딩, 합성, 인코딩 파이프라인을 그대로 실행한다.
7. 결과 버퍼만 메인 영역으로 전송하고, 배치 실행기는 기존 순서·결과 한도·다운로드 흐름을 유지한다.

로고도 같은 파일 입력 봉투로 각 Worker에 전달한다. Worker별 로고 디코딩 캐시는 유지한다. 최대 두 Worker가 최대 10MB 로고를 각각 읽을 수 있지만, 메인 영역의 로고 보관 버퍼와 복사 단계는 제거된다.

## 계약과 호환성

- 사용자에게 노출된 `image.watermark@1` 설정·결과 계약은 변경하지 않는다.
- `ImageWatermarkBatchItem`, 결과 형식, 파일 이름, MIME, 경고, 타이밍 필드는 그대로 유지한다.
- 변경 대상은 함께 배포되는 메인 런타임과 전용 Worker 사이의 내부 입력 봉투뿐이다.
- 새 의존성, 서버 처리, 네트워크 요청을 추가하지 않는다.
- 기존 최대 100개 항목, 파일당 50MB, 배치 250MB, 로고 10MB, 결과 한도를 유지한다.
- 자동 동시성은 저메모리 기기 1개, 그 외 최대 2개 Worker 정책을 유지한다.

## 진행 상태와 취소

새 공개 진행 단계는 추가하지 않는다. Worker는 파일 읽기를 기존 `validating` 단계 안에서 수행하고, 읽기가 끝난 후 기존 디코딩·합성·인코딩 진행 이벤트를 보낸다.

취소 시 현재처럼 Worker를 종료한다. `File.arrayBuffer()` 자체에 중단 신호를 연결할 수 없으므로 Worker 종료가 파일 읽기와 후속 처리를 함께 격리한다. 취소 뒤 완료 이벤트나 결과 다운로드를 만들지 않는다.

## 오류 처리와 보안 경계

Worker는 메시지 입력을 신뢰하지 않는다. 다음 경우 공개된 짧은 오류로 거부한다.

- 봉투 키, ID, 도구 버전 또는 워터마크 설정이 잘못됨
- `File`이 아니거나 이름·MIME·크기가 봉투와 다름
- 파일 읽기가 실패하거나 반환 버퍼 크기가 달라짐
- 파일·배치·결과 한도를 넘음
- 디코딩·합성·인코딩 또는 Worker가 실패함

파일 내용, 파일 이름, 미리보기, 생성 URL은 로그에 남기지 않는다. 한 항목의 정상적인 입력 오류는 해당 항목만 실패시키고 다음 항목을 처리한다. Worker 신뢰 경계가 깨진 경우에만 해당 Worker를 종료하고 기존 제한 안에서 교체한다.

## 검증

### 단위 테스트

- 배치 실행기가 원본과 로고의 `arrayBuffer()`를 호출하지 않고 `File` 봉투를 Worker에 전달함
- 잘못된 파일 이름·MIME·크기와 비네이티브 파일을 거부함
- Worker 파일 읽기 실패와 반환 크기 불일치를 안전하게 변환함
- 원본 및 로고 성공 경로가 기존 파이프라인 입력과 동일한 바이트를 전달함
- 두 Worker 배치의 순서, 결과 한도, Worker 교체, 취소 동작을 보존함

### 통합 검증

- `pnpm verify`
- 기존 이미지 워터마크 E2E를 GitHub Actions의 Chromium, Firefox, WebKit 및 모바일 프로젝트에서 실행
- 개인정보 관찰 테스트로 파일 네트워크 전송과 민감한 로그가 없음을 확인
- 브라우저 코덱 결과는 바이트 일치 대신 크기, MIME 서명, 경고와 허용 오차를 검증

## 완료 기준

- 제품 메인 코드에서 워터마크 원본·로고 `File.arrayBuffer()` 호출과 보관 버퍼가 제거됨
- 워터마크 처리 중 전체 파일 읽기부터 결과 생성까지 Worker가 소유함. 단, 지원되는 홈 런처는
  형식 감지를 위해 선택한 원본의 최대 64KiB 접두사를 읽은 뒤 `File`을 워터마크 도구에 전달할 수 있음
- 기존 워터마크 위치·화질·형식·다운로드 UX가 유지됨
- 단위 테스트, 전체 저장소 검증, 6개 브라우저 CI가 통과함
- Cloudflare Pages와 처리 스테이징 배포가 성공함
- 작업 후 임시 서버, 출력물, Docker 자원과 불필요한 작업 브랜치를 정리함

## 제외 범위

- 인코더 교체 또는 새 코덱 도입
- 워터마크 UI 재설계
- 서버 기반 워터마크 처리
- 동시 Worker 수 확대
- 결과 화질·압축률 정책 변경

인코딩 시간이 실제 병목으로 확인되면 별도 벤치마크와 설계로 다룬다.
