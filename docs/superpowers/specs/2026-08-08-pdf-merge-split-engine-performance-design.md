# PDF 합치기·분할 엔진 성능 개선 설계

**상태:** 승인됨  
**방향:** 파일 바이트를 Worker에서 순차적으로 읽어 입력 메모리 피크를 낮춘다

## 배경

현재 PDF 합치기와 분할은 브라우저 Worker에서 처리되지만, `runPdfJob`이 선택한 모든 파일을
메인 스레드에서 `arrayBuffer()`로 읽은 다음 한 번에 Worker로 전송한다. 합치기는 입력 합계가
최대 100MB이므로 처리 시작 전에 입력 전체가 JS 힙에 올라간다. Worker 안에서도 요청이 모든
입력 버퍼를 계속 참조하는 동안 출력 문서와 현재 파싱 문서가 함께 존재한다.

분할은 한 파일만 읽지만 메인 스레드에서 파일을 읽고 전송한다. 페이지별 ZIP 생성은 이미
순차적이어서 병렬화보다 현재 구조를 유지하는 편이 메모리 상한에 유리하다. 다만 fflate가
내보낸 ZIP 청크를 다시 `slice()`하여 보관하는 불필요한 복사는 제거할 수 있다.

## 목표

- 합치기 입력 전체를 메인 스레드 ArrayBuffer로 동시에 만들지 않는다.
- Worker가 한 합치기 입력을 읽고 복사한 뒤에 다음 입력을 읽는다.
- 분할 파일 읽기도 Worker로 이동해 메인 스레드의 큰 바이트 할당을 없앤다.
- 기존 ArrayBuffer 파이프라인과 파일 기반 파이프라인이 같은 합치기 코어를 사용한다.
- 결과 페이지 순서, 파일명, MIME, 경고, 제한과 직접 다운로드 동작을 유지한다.
- 새 의존성, 서버 업로드, 코덱 또는 계약 버전을 추가하지 않는다.

## 비목표

- PDF 압축률 변경
- qpdf, pdfcpu, Ghostscript, MuPDF 또는 새 WASM 런타임 도입
- 암호 PDF 처리, 서명 보존 또는 손상 PDF 복구
- 분할 ZIP을 스트리밍 파일 시스템에 직접 쓰는 새 다운로드 계약
- 합치기나 분할 UI 재설계
- 페이지 복사를 병렬화해 순간 메모리 사용량을 높이는 것

## 접근 대안

### 선택: File 구조화 복제와 Worker 순차 읽기

`File`은 브라우저의 구조화 복제 대상이다. 메인 스레드는 합치기·분할 요청에 파일 메타데이터와
`File` 객체를 넣어 Worker로 보낸다. Worker는 파일 내용을 읽는 콜백으로 감싼 뒤 파일 기반
파이프라인을 실행한다.

합치기 코어는 출력 `PDFDocument`를 한 번 만들고 입력마다 다음 순서를 지킨다.

1. 현재 파일만 `arrayBuffer()`로 읽는다.
2. 서명, 실제 바이트 길이, 암호화, 페이지 수와 누적 페이지 수를 검증한다.
3. 해당 문서의 페이지를 한 번의 `copyPages` 호출로 복사해 공유 리소스 중복을 막는다.
4. 현재 입력과 파싱 문서에 대한 참조를 반복문 밖으로 넘기지 않는다.
5. 마지막 입력까지 처리한 뒤 결과를 한 번 직렬화한다.

기존 `runPdfPipeline`의 ArrayBuffer 합치기도 같은 코어에 즉시 해결되는 읽기 콜백을 전달한다.
따라서 테스트, 서버 호환 경로와 브라우저 파일 경로가 서로 다른 PDF 결과 알고리즘을 갖지 않는다.

### 제외: 처리 후 입력 ArrayBuffer 강제 detach

코드 양은 적지만 `PDFDocument`가 원본 버퍼를 늦게 참조할 가능성을 라이브러리 내부 구현에
의존한다. 처리 전 메인 스레드가 모든 파일을 읽는 피크도 줄이지 못한다.

### 제외: 전용 서버 또는 WASM 엔진

일부 문서에서 더 강한 최적화를 제공할 수 있지만 업로드 고지, 서버 비용, 바이너리 출처,
라이선스, 번들 크기와 다중 런타임 운영이 추가된다. 현재 문제는 PDF 알고리즘이 아니라 입력
수명 관리이므로 플랫폼 `File`과 기존 MIT 라이브러리로 해결한다.

## 구성 요소와 계약

### 파일 기반 Worker 요청

기존 Worker 프로토콜 1에 `run-files` 요청을 추가한다. 이 요청은 합치기와 분할에만 허용한다.
각 입력은 `name`, `mimeHint`, `byteLength`, `file`을 가진다. 도구 버전과 PDF 명세 버전은
그대로 1을 사용한다.

Worker는 요청 도구와 명세가 일치하는지 확인하고, 파일 객체의 `name`, `type`, `size`가 함께
전달된 메타데이터와 일치하는지 검증한다. 불일치나 파일 읽기 실패는 기존 오류 계약으로 매핑한다.

### 파일 기반 파이프라인

브라우저 런타임에 파일 메타데이터와 `readBytes()`를 가진 내부 입력 타입을 둔다.
`runPdfFilePipeline`은 합치기라면 증분 합치기 코어를 호출하고, 분할이라면 단일 파일을 Worker에서
읽은 뒤 기존 분할 코어를 호출한다. 다른 작업은 기존 `run` 요청을 유지한다.

### ZIP 청크 수명

`ZipPassThrough`가 전달한 청크는 fflate가 새로 소유해 내보낸 바이트이므로 청크 배열에 그대로
보관한다. 최종 연속 ArrayBuffer 생성은 현재 결과 계약상 한 번 필요하지만 청크마다 하던 추가
`slice()`는 제거한다.

## 데이터 흐름

~~~text
메인 스레드
  File[] --structured clone--> PDF Worker

PDF Worker (merge)
  File 1 read -> parse -> copy pages -> release source
  File 2 read -> parse -> copy pages -> release source
  ...
  output save -> transferable ArrayBuffer -> 메인 스레드

PDF Worker (split)
  File read -> parse once -> page PDF sequential creation -> ZIP -> result
~~~

메인 스레드는 합치기·분할에서 `File.arrayBuffer()`를 호출하지 않는다. 입력 바이트의 불가피한
최대 수명은 Worker 안의 현재 파일 처리 구간으로 제한된다. 출력 문서와 최종 결과 바이트는 결과를
만들기 위해 필요하므로 유지한다.

## 오류와 취소

- 파일 수와 선언 용량은 메인 요청을 만들기 전과 Worker 파이프라인 양쪽에서 검증한다.
- 실제 읽은 길이가 `File.size`와 다르면 손상 또는 읽기 실패로 처리한다.
- 취소 시 기존처럼 Worker를 즉시 종료하므로 진행 중 파일 읽기와 파싱도 함께 중단된다.
- 암호, 페이지 수, 압축 해제 안전 한도, 출력 크기 오류는 기존 코드와 한국어 메시지를 유지한다.
- 파일명, 파일 내용, 썸네일, ArrayBuffer 또는 결과 URL은 로그에 남기지 않는다.

## 테스트 전략

- `runPdfJob` 단위 테스트에서 합치기·분할이 메인 스레드의 `File.arrayBuffer()`를 호출하지 않고
  `run-files` 요청을 보내는지 먼저 실패로 확인한다.
- 파일 기반 합치기 테스트는 실제 PDF를 사용하고, 두 번째 입력 읽기가 첫 번째 문서의
  `copyPages` 완료 뒤에 일어나는지 확인한다.
- ArrayBuffer 경로와 파일 경로 모두 페이지 순서, 메타데이터, MIME과 경고가 동일한지 검증한다.
- 분할 파일 경로로 실제 ZIP을 열어 파일명, 페이지 수와 크기를 확인한다.
- 기존 PDF 단위 테스트, 전체 `pnpm verify`, 다중 브라우저 E2E를 실행한다.
- 브라우저 테스트는 실제 Worker와 `File` 구조화 복제를 통과해야 한다.

## 완료 기준

- 합치기·분할 실행 시 메인 스레드는 입력 파일 바이트를 읽지 않는다.
- 합치기는 다음 파일을 읽기 전에 현재 파일의 페이지 복사를 완료한다.
- 기존 출력과 사용자 흐름에 회귀가 없다.
- 새 의존성과 네트워크 요청이 없다.
- 전체 CI와 Cloudflare Pages 프로덕션 배포가 성공한다.
