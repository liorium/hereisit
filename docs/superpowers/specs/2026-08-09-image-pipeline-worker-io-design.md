# 공통 이미지 파이프라인 Worker 파일 I/O 설계

## 목표

이미지 크기 조절과 형식 변환이 사용하는 `runImageBatch()`에서 원본 파일 읽기를 전용 Worker가 소유하도록 바꾼다. 스마트 로컬 압축이 이 공통 파이프라인을 호출할 때 발생하는 두 번째 UI 영역 전체 파일 읽기도 제거한다.

기존 이미지 검사, 디코딩, 변환, 인코딩 알고리즘과 결과 화질은 바꾸지 않는다. 주된 성공 기준은 제품 메인 코드의 `runImageBatch()`가 `File.arrayBuffer()`를 호출하거나 원본 바이트를 보관하지 않는 것, 그리고 기존 결과·진행률·오류·취소 동작을 유지하는 것이다.

## 현재 흐름과 문제

현재 배치 실행기는 항목마다 `File.arrayBuffer()`를 호출하고 `ArrayBuffer`를 Worker로 전송한다. 최대 두 Worker가 동작할 때 UI 영역이 여러 파일 읽기, 작업 예약, 진행 이벤트를 함께 담당한다.

- 파일당 최대 50MiB의 버퍼가 UI 영역에서 할당된다.
- Worker 전송 전 파일 읽기를 기다려 첫 처리 피드백이 늦어진다.
- 취소와 Worker 교체를 위해 `generation` 상태가 필요하다.
- 스마트 로컬 압축은 자체 검사 읽기 뒤 공통 배치 실행기에서 같은 파일을 다시 읽는다.
- Worker가 TypeScript 타입만 믿고 런타임 메시지와 파일 메타데이터를 충분히 검증하지 않는다.

## 검토한 접근

### 1. 기존 이미지 Worker에 네이티브 `File` 전달 — 선택

배치 실행기가 파일 메타데이터와 네이티브 `File`을 구조화 복제로 보내고, 기존 Worker가 검증·읽기 후 바이트 기반 파이프라인을 호출한다. 이미 검증된 이미지 워터마크 구조를 재사용하므로 변경 범위가 작고 결과 알고리즘을 건드리지 않는다.

### 2. 압축 선택과 무손실 메타데이터 처리까지 동시에 Worker화

UI 영역 전체 읽기를 더 많이 제거할 수 있지만 압축 전용 계약, 서버 대체 경로, 순수 메타데이터 제거까지 함께 바꿔야 한다. 독립적으로 검증해야 할 별도 작업이므로 이번 범위에서 제외한다.

### 3. UI에서 제한된 접두사만 읽어 직접 검사

메모리는 작지만 큰 JPEG 메타데이터 뒤에 치수 정보가 있는 정상 파일을 잘못 거부할 수 있다. 처리 정확도를 낮추므로 선택하지 않는다.

## 계약과 데이터 흐름

1. UI는 기존 `BatchImageItem` 계약대로 `File`, 항목 ID, 변환 설정을 전달한다.
2. 배치 실행기는 `{ name, mimeHint, byteLength, file }` 봉투를 유휴 Worker에 구조화 복제한다. `File`에는 전송 목록을 사용하지 않는다.
3. Worker는 메시지의 정확한 키, 프로토콜, 작업 ID, 도구 ID와 버전, 설정, 네이티브 `File` 여부를 검증한다.
4. Worker는 봉투 이름·MIME·크기와 실제 `File` 메타데이터가 일치하며 크기가 1바이트 이상 50MiB 이하인지 확인한다.
5. Worker가 `File.arrayBuffer()`를 호출하고 반환값이 일반 `ArrayBuffer`이며 선언된 길이와 일치하는지 확인한다.
6. 검증된 바이트를 기존 `processImagePipeline()`에 전달한다.
7. 결과 버퍼만 전송 목록으로 UI 영역에 반환한다.

공통 파일 봉투 타입은 도구 계약 패키지에 하나만 두고 이미지 파이프라인과 이미지 워터마크 타입 별칭이 함께 사용한다. 공개 `BatchImageItem`과 바이트 기반 파이프라인 입력은 유지한다.

`image.pipeline`의 사용자 설정·결과 계약은 바뀌지 않으므로 `IMAGE_TOOL_VERSION = 2`를 유지한다. 변경 대상은 함께 빌드·배포되는 배치 실행기와 Worker 사이 내부 운송 방식이다.

브라우저가 구조화 복제 과정에서 `File` 데이터를 어떤 방식으로 구현하는지는 성능 보장에 포함하지 않는다. 보장하는 것은 제품 UI 코드가 전체 파일 `ArrayBuffer`를 만들거나 Worker 전송용으로 보관하지 않는 구조다.

## 상태, 진행률과 취소

- 기존 자동 동시성 정책인 저메모리 기기 1개, 그 외 최대 2개 Worker를 유지한다.
- 파일 읽기는 기존 `validating` 단계에 포함하며 새 공개 단계를 추가하지 않는다.
- Worker가 파일을 읽는 동안 취소되면 해당 Worker를 종료하고 늦은 결과나 진행 이벤트를 무시한다.
- Worker 내부에서도 취소 ID를 확인해 읽기 후 파이프라인 실행과 완료 이벤트를 차단한다.
- UI 영역의 비동기 파일 읽기가 사라지므로 쓰기 전용이 되는 `WorkerSlot.generation` 상태는 삭제한다.
- 항목 순서, 항목별 180초 제한, Worker 장애 교체, 배치 완료 의미를 유지한다.

## 오류와 신뢰 경계

- 상관관계에 사용할 수 있는 유효 작업 ID가 있는 잘못된 요청은 `INVALID_SPEC`으로 종료한다.
- 파일 크기 제한 위반은 기존 `MEMORY_LIMIT` 의미를 유지한다.
- 파일 읽기 거부는 재시도 가능한 `CORRUPT_INPUT`으로 변환한다.
- 비정상 버퍼 또는 읽은 길이 불일치는 재시도 불가능한 `CORRUPT_INPUT`으로 변환한다.
- 잘못된 Worker 이벤트, 작업 ID, 순서, 결과 버퍼 또는 결과 길이는 신뢰하지 않는다. 해당 항목을 안전한 `WORKER_CRASH` 또는 기존 한도 오류로 종료하고 필요하면 Worker를 교체한다.
- 파일 내용, 파일 이름, 미리보기, 객체 URL과 생성 결과 URL은 로그에 남기지 않는다.

## 유지할 한도와 동작

- 입력 파일당 최대 50MiB
- 입력 이미지 최대 50,000,000픽셀 및 한 변 16,384픽셀
- 출력 최대 25,000,000픽셀, 파일당 100MiB
- 배치 결과 합계 최대 500MiB
- Worker 최대 2개와 작업당 180초 제한
- 기존 JPG·PNG·WebP·HEIC 검사와 지원 정책
- 기존 크기 조절, 자르기, 형식, 품질, 파일명, 경고, 타이밍, 다운로드 UI
- 네트워크 요청이나 서버 대체 경로를 새로 추가하지 않음

## 검증

### 계약과 배치 단위 테스트

- 배치 실행기가 원본 `File.arrayBuffer()`를 호출하지 않음
- 네이티브 `File` 봉투를 전송 목록 없이 Worker에 전달함
- 자동·명시 동시성, 항목 순서, 결과 500MiB 한도와 Worker 교체를 유지함
- 읽기 대기 중 취소가 한 번만 정산되고 늦은 이벤트를 무시함

### Worker 단위 테스트

- 정상 파일을 Worker에서 읽어 기존 파이프라인에 같은 바이트로 전달함
- 정확한 키가 아닌 요청, 비네이티브 파일, 이름·MIME·크기 불일치를 거부함
- 파일 읽기 실패, 비정상 `ArrayBuffer`, 반환 길이 불일치를 공개 오류로 변환함
- 잘못된 도구 버전·설정과 동시 요청, 취소 뒤 완료 이벤트를 차단함

### 통합 검증

- 집중 Vitest의 RED → GREEN 기록
- `pnpm verify`
- 보호된 GitHub Actions에서 Chromium, Firefox, WebKit 및 모바일 프로젝트와 제품 분석 테스트 통과
- Cloudflare Pages와 처리 스테이징 배포 성공

브라우저 코덱 결과는 바이트 일치가 아니라 크기, MIME 서명, 경고와 허용 오차로 검증한다.

## 완료 기준

- `run-image-batch.ts`에서 원본 `File.arrayBuffer()`와 전송용 원본 버퍼가 제거됨
- 크기 조절·형식 변환 전체 파일 읽기부터 결과 생성까지 Worker가 소유함
- 스마트 로컬 압축의 공통 배치 단계에서 발생하던 추가 UI 영역 전체 읽기가 제거됨
- 기존 사용자 결과와 한도 및 다운로드 UX가 유지됨
- 단위·통합·퍼즈·빌드·6개 브라우저 CI가 통과함
- 병합 후 Pages와 처리 스테이징 배포가 성공함
- 임시 worktree, 작업 파일, Docker 이미지와 빌드 캐시가 정리됨

## 제외 범위

- 이미지 압축 파일 선택 단계의 최초 전체 파일 검사
- 무손실 로컬 압축의 메타데이터 검사·제거용 전체 파일 읽기
- 인코더·코덱·품질 정책 변경
- UI 재설계 또는 새 기능
- Worker 수 확대와 서버 처리 변경

압축 최초 읽기와 무손실 경로는 결과 동일성을 보존하는 별도 설계와 테스트로 후속 최적화한다.
