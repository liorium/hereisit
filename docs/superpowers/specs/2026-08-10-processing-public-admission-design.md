# 이미지 압축 서버 처리 100% 공개 설계

## 목표

검증된 이미지 압축 서버 엔진을 모든 적격 사용자에게 기본 처리 경로로 공개한다. 공개 비율은
`100%`로 고정하며, 현재 프로덕션에 적용된 월 예상비용 상한 `5,000,000µUSD`(5달러), 일일
사용량, 동시 작업, 네트워크와 대기열 한도를 유지한다.

파일은 화면에 표시된 임시 서버 처리 고지 뒤에만 전송한다. 비용, 처리 검증, 삭제, 대기열 또는
사용량 집계 안전 조건이 깨지면 기존 회로차단기가 서버 입장을 즉시 거부하고 브라우저 로컬 처리로
복귀시킨다.

## 현재 상태

현재 릴리스 흐름은 성공한 `main` CI의 정확한 커밋과 스테이징 엔진 이미지 digest를 프로덕션에
배포한다. 보호된 `processing-production` 환경 승인 뒤 다음 검증을 마친다.

- Worker 모듈, 생성 설정, 엔진 digest와 소스 SHA의 버전 증명
- 분리된 D1, R2, Queue, DLQ, Analytics와 Logpush 바인딩
- 새 비용 집계 epoch와 공급자 사용량 대조
- 관리자 전용 실제 업로드, 처리, 다운로드와 삭제 스모크
- 프로덕션 Pages 배포와 정확한 SHA 검증

프로덕션 Worker의 공개 비율만 `0%`이며 등록된 관리자 세션만 서버 처리를 사용한다. 정책, 작업 생성,
D1 예약과 Queue 소비자는 이미 비율·할당량·회로 상태를 각각 재검증한다. 따라서 새 처리 시스템은
필요하지 않다. 필요한 것은 검증된 동일 릴리스를 안전하게 `0%`에서 `100%`로 승격하고 필요 시
`0%`로 되돌리는 운영 경로다.

## 검토한 접근

### 1. 검증된 프로덕션 릴리스의 별도 보호 승격 — 선택

기존 프로덕션 배포는 관리자 canary `0%`로 끝낸다. 성공한 canary 산출물을 입력으로 같은
`processing-production` 보호 환경과 직렬화 잠금에서 공개 비율만 `100%`인 새 Worker 버전을 만든다.
엔진, Worker 코드, 비용 모델과 모든 한도는 바뀌지 않아야 한다.

배포 검증과 공개 전환이 분리되므로 canary 실패가 공개 사용자에게 닿지 않고, 공개 전환만 독립적으로
되돌릴 수 있다. 이미 있는 빌드, 설정 생성, 버전 증명, D1 적용과 스모크 코드를 확장해 사용한다.

### 2. 기존 프로덕션 배포를 바로 `100%`로 변경

파일 수는 적지만 공개 설정이 실제 프로덕션 canary보다 먼저 활성화된다. 후속 스모크 실패 시 별도
복구 배포가 필요하고 배포 결함과 공개 승격 결함을 구분하기 어렵다. 선택하지 않는다.

### 3. `5% → 25% → 100%` 단계 승격

트래픽이 충분할 때는 유효하지만 현재는 표본이 작아 각 단계가 의미 있는 통계를 만들지 못한다.
임의 비율 입력과 여러 운영 상태만 늘어난다. 이번 작업은 `0%`와 `100%` 두 상태만 지원한다.

## 운영 구조

### 프로덕션 canary 배포

`.github/workflows/processing-production.yml`은 현재 책임을 유지한다. 성공한 스테이징 SHA와 immutable
엔진을 프로덕션에 `0%`로 배포하고 관리자 실제 스모크를 통과시킨 뒤, 공개 승격에 필요한 기존의
sanitized 산출물을 보관한다.

새 프로덕션 릴리스가 들어오면 이전 공개 릴리스가 있더라도 먼저 새 버전을 `0%` canary로 검증한다.
이 짧은 구간의 일반 사용자는 로컬 처리를 사용한다. 새 canary가 성공한 뒤에만 같은 SHA의 공개 승격이
가능하다.

### 공개 승격과 비상 비활성화

하나의 작은 운영 workflow가 두 동작만 제공한다.

- 성공한 `Processing production` 실행 뒤의 공개 승격: `0% → 100%`
- 보호된 수동 비상 비활성화: 현재 공개 릴리스 `100% → 0%`

두 동작은 기존 프로덕션 배포와 같은 `processing-production` 직렬화 그룹과 보호 환경을 사용한다.
임의 비율, 엔진 선택, 가격 또는 한도 입력은 받지 않는다. 승격은 트리거한 canary 실행의 정확한
run ID, head SHA와 산출물만 사용하고 비활성화는 현재 배포 상태를 다시 읽어 stale 요청을 거부한다.

승격 workflow는 코드를 새로 선택하거나 엔진을 다시 빌드하지 않는다. 정확한 SHA를 checkout하고
잠긴 의존성으로 Worker bundle과 비용 모델을 재현한 뒤 canary 증명에 기록된 hash와 비교한다. 기존
Cloudflare 리소스를 조회해 계정, Worker, D1, R2, Queue, Logpush와 immutable 엔진 digest가 canary
산출물 및 실제 배포와 일치하는지 확인한다.

### Worker 버전 증명

기존 `verify-worker-version-chain.mjs`와 D1 적용 경로를 확장한다. 별도의 증명 체계를 추가하지 않는다.

승격은 다음 조건을 모두 요구한다.

1. 현재 활성 Worker 버전이 성공한 canary의 활성 버전이다.
2. 새 버전은 Wrangler가 만든 정확히 한 번의 Worker upload다.
3. Worker 모듈, release SHA, 엔진 digest, 리소스, 한도, 비용 모델, 관리자 목록과 비밀 바인딩은
   canary와 같다.
4. 생성 설정의 허용된 차이는 공개 비율 `0`에서 `100`뿐이다.
5. 새 버전을 D1의 유일한 active 버전으로 등록하고 이전 active 버전을 retiring 처리한 뒤에만
   공개 정책을 성공으로 판정한다.

비상 비활성화도 같은 검사를 반대로 수행한다. 복구 중 일부 증명 기록이 실패하더라도 공개 비율
`0%` 설정 배포와 Queue 정지는 독립적으로 시도해 항상 fail closed로 끝낸다.

## 승격 데이터 흐름

1. 성공한 프로덕션 canary workflow의 run ID, head SHA와 artifact ID를 GitHub가 전달한다.
2. 승격 workflow가 exact SHA를 checkout하고 artifact의 source SHA, engine digest, Worker 증명,
   gate 결과와 canary 결과를 검증한다.
3. Cloudflare 실제 Worker 버전, D1 active 증명, Container digest, 비용 epoch, 회로 상태와 Queue 상태를
   읽는다. 불일치, 열린 회로, 미완료 비용 집계, 삭제 지연 또는 활성 작업이 있으면 자격 증명 사용
   이후의 변경 전에 중단한다.
4. primary Queue를 일시 정지하고 DLQ가 계속 정지 상태인지 확인한다. 진행 중 작업과 outbox가 없는
   상태를 확인한다.
5. 같은 Worker와 한도를 사용하고 공개 비율만 `100%`인 설정을 생성한다. 동시에 비상용 `0%` 설정을
   생성해 두 설정의 허용된 차이가 비율뿐인지 검증한다.
6. `100%` Worker 버전을 no-bundle로 배포하고 버전 전이를 검증해 D1에 증명한다.
7. 실제 프로덕션 정책 요청이 일반 익명 세션에 `execution: server`, `upload: true`와 삭제 고지를
   반환하는지 확인한다.
8. primary Queue만 재개하고 일반 익명 사용자 조건으로 작은 이미지의 업로드, 처리, 직접 다운로드,
   다운로드 확인과 삭제 스모크를 실행한다.
9. Queue가 재개됐고 DLQ가 정지됐으며 임시 입력·결과와 고아 작업이 남지 않았는지 확인한다.
10. source SHA, 이전/새 Worker 버전, rollout `100`, 정책·스모크·정리 결과만 포함한 sanitized artifact를
    7일 보관한다.

## 비용과 사용량 경계

기존 프로덕션 값을 그대로 사용한다.

- 월 예상비용 상한: `5,000,000µUSD`(5달러)
- 1,000개 처리당 live 비용 상한: `500,000µUSD`(0.50달러)
- account, anonymous, network 일일 weighted-unit 한도: 기존 production canary 값
- account pending 작업: 10개
- network pending 작업: 3개
- 최대 Queue 대기: 600초
- 세션, 네트워크, 상태 조회, 다운로드와 정책 API의 기존 Cloudflare Rate Limit

비용 상한은 결제 한도를 직접 생성하는 기능이 아니라 서버 입장을 차단하는 제품 안전 경계다. 현재
hourly cost sealer와 provider/logpush 대조가 예상 월비용, 1,000건당 비용 또는 집계 무결성 위반을
확인하면 D1 회로를 연다. 회로가 열리면 `100%` 설정이 남아 있어도 정책과 작업 생성은 서버 처리를
거부하고 UI는 로컬 처리로 복귀한다. 회로는 자동으로 다시 열지 않는다.

## 사용자 경험과 개인정보

새 UI나 선택 화면은 추가하지 않는다. 이미지 압축 화면의 기존 정책 응답을 사용한다.

- 서버 정책일 때만 임시 서버 전송과 삭제 정책을 명확히 표시한다.
- 로컬 대체일 때는 업로드하지 않고 기존 로컬 Worker 처리를 사용한다.
- 서버 처리 중 재시도 가능한 실패는 기존 규칙대로 로컬 처리로 대체한다.
- 결과 화면은 이전/이후 용량과 다운로드 동작을 유지한다.

파일 내용, 파일명, 썸네일, presigned URL은 로그나 배포 artifact에 기록하지 않는다. 브라우저는 R2
자격 증명을 받지 않으며 Worker origin을 통해서만 업로드한다.

## 실패와 복구

- 승격 전 검증 실패: 아무것도 변경하지 않고 현재 `0%` 상태를 유지한다.
- Queue 정지 뒤 배포 전 실패: primary Queue를 이전 상태로만 복구하고 rollout은 `0%`다.
- `100%` 배포 뒤 검증 또는 스모크 실패: primary Queue를 정지하고 준비된 `0%` 설정을 배포한 뒤
  실제 정책이 `local`, `upload: false`인지 확인한다. 두 복구 동작은 한쪽 실패가 다른 쪽을 막지
  않게 각각 시도한다.
- 운영 중 비용·삭제·검증·Queue·집계 이상: 기존 회로차단기가 즉시 로컬 정책을 반환한다. 운영자가
  원인을 확인한 뒤 보호된 비상 비활성화로 설정도 `0%`에 고정한다.
- GitHub Actions 또는 Cloudflare 일시 장애: 공개 상태를 추측해 덮어쓰지 않는다. 실제 Worker와 D1
  상태를 다시 조회한 새 실행만 허용한다.

실패 workflow는 성공으로 위장하지 않는다. 복구 시도와 최종 공개 상태를 artifact에 기록한 뒤 원래
실패를 유지한다.

## 검증

### 단위와 workflow 계약

- 승격 증명은 exact canary SHA/run/artifact와 현재 active Worker가 다르면 거부한다.
- 설정 비교는 rollout `0 ↔ 100` 외의 모든 차이를 거부한다.
- 월 상한 5달러, live 비용 상한, 할당량과 Rate Limit이 canary와 동일함을 검증한다.
- 열린 회로, 미완료 비용 집계, 삭제 지연, 진행 중 작업과 잘못된 Queue 상태를 거부한다.
- 새 Worker 버전 하나만 허용하고 D1 active/retiring 상태를 원자적으로 확인한다.
- 실패 경로가 primary Queue 정지와 `0%` 정책 복귀를 각각 시도함을 workflow 테스트로 고정한다.
- artifact allowlist에 파일 정보, URL, 자격 증명 또는 전체 Cloudflare 응답이 들어가지 않음을 검증한다.

### 전체 검증과 배포

- 집중 테스트 RED → GREEN
- `pnpm verify`
- 보호된 GitHub Actions의 Chromium, Firefox, WebKit, 모바일 3종과 제품 분석
- 성공한 exact-SHA 처리 스테이징과 관리자 전용 프로덕션 canary
- 보호된 공개 승격
- 익명 프로덕션 정책, 실제 압축, 직접 다운로드, 삭제와 고아 작업 없음 확인
- 승격 artifact와 실제 Cloudflare/D1 상태의 최종 교차 확인

로컬 서버 자원은 비브라우저 검증에만 사용한다. Playwright 전체 브라우저 행렬과 WebKit은 기존
GitHub Actions 경로에서 실행한다.

## 완료 기준

- 일반 익명 세션의 프로덕션 정책이 정상 상태에서 `execution: server`와 `upload: true`를 반환한다.
- 공개 비율은 정확히 `100%`이며 임의 비율 경로가 없다.
- 월 예상비용 상한은 정확히 5달러이고 기존 비용·할당량·Rate Limit 경계가 유지된다.
- 열린 회로 또는 한도 초과 시 정책과 작업 생성이 fail closed로 로컬 처리에 복귀한다.
- 익명 실제 압축이 처리, 다운로드, 확인 삭제까지 성공하고 임시 객체와 고아 작업을 남기지 않는다.
- 보호된 비상 비활성화가 실제 정책을 `local`, `upload: false`로 되돌린다.
- CI, 브라우저 행렬, 스테이징, 프로덕션 canary와 공개 승격이 모두 성공한다.
- 완료 뒤 임시 파일, 테스트 출력, Docker 리소스와 작업 worktree를 정리한다.

## 제외 범위

- 결제, 로그인, 유료 요금제와 사용자별 과금
- PDF 또는 다른 도구의 서버 처리 공개
- 새 코덱, 압축 품질, 파일 크기와 픽셀 한도 변경
- `5%`나 `25%` 같은 중간 단계와 임의 rollout 입력
- Cloudflare 결제 수단의 실제 청구를 막는 계정 단위 hard cap
- UI 재설계, 새 설정 화면 또는 새 의존성
