# 이미지 엔진 품질 벤치마크 갱신 설계

## 목표

현재 프로덕션 이미지 엔진을 소유한 테스트 이미지로 다시 측정해 JPEG·PNG·WebP의 압축 결과, 처리 시간, 최대 메모리와 예상 비용을 확인한다. 측정에서 실제 회귀가 드러날 때만 가장 작은 엔진 또는 검사 수정으로 해결한다.

새 기능, UI 변경과 처리 비율 승격은 하지 않는다. 존재하는 코퍼스, 네이티브 엔진, 측정 도구와 GitHub Actions 워크플로를 재사용하며 새 의존성과 외부 이미지 수집을 추가하지 않는다.

## 현재 상태

- 품질 워크플로는 수동 실행이며 마지막 기록은 2026-07-31이다. 이후 이미지 엔진과 브라우저 Worker 경계가 여러 차례 변경됐다.
- `tests/image-corpus`에는 HereIsIt 소유 이미지 24개 이상과 해시, 형식, 치수, 알파, 색상 프로필, 콘텐츠 분류가 고정돼 있다.
- `benchmark-image-engine.mjs`는 실제 네이티브 엔진으로 JPEG·PNG·WebP를 처리하고 SSIMULACRA2, Butteraugli, 결과 크기, 처리 시간, 최대 메모리와 비용을 기록한다.
- 현재 CI는 최대 20개의 작은 이미지와 `smart/balanced`만 측정하는 `pr` 범위를 사용한다.
- `pr` 판정은 표본 수, 세 형식, 90% 성공률, 알파 보존과 더 커진 결과 미선택만 검사한다. 측정된 화질·시간·메모리·비용은 보고서에 있지만 합격 판정에는 사용하지 않는다.
- 별도의 `release` 판정기는 사람 평가, 승인된 경쟁사 비교와 운영 지연을 요구한다. 현재 자동 벤치마크는 이 데이터를 생성하지 않으므로 출시급 통과를 자동으로 주장할 수 없다.

## 검토한 접근

### 1. 최신 엔진 실측 후 기존 기준만 최소 연결 — 선택

현재 `main`의 정확한 커밋에서 기존 수동 워크플로를 실행하고 보고서를 검증한다. 결과가 정상이라면 이미 문서화된 출시 기준 중 현재 보고서가 실제로 측정하는 항목만 `pr` 판정에 연결한다. 실패가 있으면 원인을 재현한 뒤 해당 경계만 수정하고 같은 벤치마크를 다시 실행한다.

이 접근은 현재 장치를 재사용하고, 측정 없이 코덱 값을 바꾸지 않으며, 자동화할 수 없는 사람·경쟁사 데이터를 꾸미지 않는다.

### 2. 출시급 판정을 한 번에 자동화

사람 평가 시스템, 경쟁사 승인 자료, 운영 환경 지연과 삭제 수명 측정을 모두 연결할 수 있지만 별도 제품·운영 프로젝트가 된다. 이번 성능 점검보다 범위가 크고 외부 서비스 약관과 반복적인 사람 검토가 필요하므로 선택하지 않는다.

### 3. 코덱 프리셋을 먼저 조정

빠르게 수치가 달라질 수 있지만 현재 회귀나 병목 증거가 없고 특정 코퍼스에 과적합할 수 있다. 측정 전 변경은 선택하지 않는다.

## 실행 흐름

1. 깨끗한 `main`의 정확한 커밋과 엔진 소스 잠금 파일을 기록한다.
2. 기존 `Image quality benchmark` 워크플로를 한 번 실행한다.
3. 워크플로가 엔진과 지표 도구를 한 번 빌드하고, 소유 코퍼스 해시와 메타데이터를 검증한다.
4. `smart/balanced` 범위에서 JPEG·PNG·WebP를 실제 처리하고 정규화된 보고서를 생성한다.
5. 보고서의 엔진 이미지 digest, 소스 잠금·코퍼스·비용 모델 해시가 실행 커밋과 일치하는지 확인한다.
6. 형식별 성공률, 원본 유지, 출력 비율, SSIMULACRA2, Butteraugli, 처리 시간, 최대 메모리와 예상 비용을 요약한다.
7. 아래 결정 규칙에 따라 코드 변경 여부를 정한다.

## 결정 규칙

### 벤치마크 또는 계약 실패

해시 불일치, 지원 형식 누락, 알파 손상, 더 큰 결과 선택 또는 90% 미만 성공률은 차단한다. 실패를 가장 작은 단위 테스트로 재현하고 공통 원인 한 곳만 수정한다.

### 측정 가능한 출시 기준 실패

현재 보고서로 계산 가능한 기존 기준만 사용한다.

- JPEG·WebP 처리 시간 p95 3초 이하
- 표준 PNG 처리 시간 p95 8초 이하
- 일반 입력 최대 메모리 512MiB 이하
- 선택된 출력이 입력보다 크지 않음
- 무손실 또는 알파 검증 불일치 없음

실패하면 해당 형식과 콘텐츠 분류를 재현하는 기존 코퍼스 사례로 엔진 정책을 점검한다. 품질과 크기의 교환을 바꾸는 수정은 SSIMULACRA2와 Butteraugli가 함께 악화되지 않는다는 증거가 있어야 한다.

### 모두 통과

엔진 코드는 바꾸지 않는다. 현재 `pr` 판정이 이미 생성된 시간·메모리 결과를 무시한다면, 위의 고정된 기존 기준만 최소한으로 연결하고 단위 테스트를 추가한다. 새 기준값이나 별도 구성 파일은 만들지 않는다.

### 자동화할 수 없는 출시 기준

사람 평가, 승인된 경쟁사 비교, 실제 운영의 취소·정책·업로드·삭제 지연은 이번 결과에서 `미검증`으로 남긴다. 5% 처리 비율 승격은 이 항목과 비용·오류율을 별도 승인한 뒤 진행한다.

## 신뢰 경계와 데이터 정책

- 코퍼스는 `HereIsIt-Owned-1.0` 또는 CC0로 이미 허용된 저장소 파일만 사용한다.
- 외부 사이트 파일 수집, 경쟁사 결과 스크래핑과 사용자 파일 사용을 하지 않는다.
- 보고서에는 파일 내용, 파일명, 썸네일, presigned URL을 기록하지 않는다.
- 엔진 이미지와 입력 코퍼스는 digest와 SHA-256으로 실행 결과에 결합한다.
- GitHub Actions 산출물은 기존 14일 보존 정책을 유지한다. 영구 대용량 벤치마크 산출물을 저장소에 커밋하지 않는다.

## 검증

- 기존 전체 기준: `pnpm verify`
- 변경이 생길 경우: 관련 판정 또는 엔진 테스트에서 RED → GREEN
- 변경 후 전체 기준: `pnpm verify`
- 정확한 최종 커밋에서 `Image quality benchmark` 통과
- PR이 필요할 경우 보호된 GitHub CI와 Cloudflare Pages 통과 후 병합
- 엔진 변경이 있을 경우에만 처리 스테이징과 인증된 smoke를 통과한 뒤 프로덕션 배포

## 완료 기준

- 최신 `main`과 불변 엔진 digest에 결합된 벤치마크 보고서가 존재한다.
- JPEG·PNG·WebP가 모두 측정되고 기존 `pr` 판정을 통과한다.
- 결과 크기, 화질 지표, 처리 시간, 최대 메모리와 예상 비용을 확인할 수 있다.
- 실패가 있으면 재현 테스트와 최소 수정 뒤 같은 워크플로가 통과한다.
- 실패가 없으면 엔진을 불필요하게 변경하지 않는다.
- 자동 검증 범위와 미검증 출시 조건을 구분해 기록한다.
- 임시 worktree, 로컬 컨테이너, 벤치마크 파일과 작업 전용 Docker 캐시는 완료 후 정리한다.

## 제외 범위

- 새 이미지 기능 또는 UI 변경
- 새 코덱, 의존성, 코퍼스 다운로드 시스템
- 외부 서비스 무단 측정과 경쟁사 스크래핑
- 사람 평가 결과의 자동 생성 또는 대체
- 이미지 서버 처리 비율의 5% 승격
- 전체 출시 판정기를 이번 작업에 맞춰 약화하는 변경
